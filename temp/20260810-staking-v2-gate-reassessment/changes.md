# 변경 내역 — 스테이킹 v2 PRD 게이트 재평가 (마스터 답변 반영)

## 왜 (Why)

마스터가 `staking-payout-rail-prd.md` §5.1 질의서의 Q1/Q3/Q4/Q5/Q6/Q7에 직접 답변했다.
이 답변이 `staking-yield-system-v2-prd.md` §13의 최우선 차단 항목(B-1/B-2/B-2b)과
§9의 G-0′를 해소하는지 재평가해야 한다.

**핵심 판단: 해소되지 않았다. 그러나 질문의 형태가 바뀌었고, 차단 항목의 수는 7개에서 3개로 줄었다.**

## 무엇이 바뀌는가 (What)

### 1. 새 검증 사실 추가 (§2에 N-9 ~ N-12)
- **N-9**: `schema.prisma` 전체에 `balance` 필드가 **존재하지 않는다**. BANA는 로컬 잔고 원장을
  갖고 있지 않으며, 사용자 잔고는 전량 허브 `GET /api/v1/wallets`에서 온다
  (`api/nia/balance/route.ts:14`).
- **N-10**: `forwardWithdrawalToHub`는 **차변(debit)** 호출이다 — `userId: wr.niaUserId` 기준으로
  허브에 출금을 지시한다(`withdrawals.ts:35-46`). 크레딧 수단이 아니다.
- **N-11**: 사용자 주도 스테이킹은 **허브 잔고가 있어야만** 성립한다
  (`stake/route.ts:100-101, 138-144`). 즉 허브가 BANA를 자산으로 인식하지 못하면 스테이킹 자체가
  단 한 건도 성공할 수 없다 → Q3 답변("추가하면 된다")과 코드 사이에 검증 가능한 모순이 있다.
- **N-12**: 출금 수수료·최소 출금 단위는 이미 존재하나 **허브가 공급**한다
  (`Withdraw.tsx:97-98` — `withdrawFee`/`minWithdrawAmount`). 관리자 추가 커스텀 코인
  (`ManagedCoin`)은 `fee: '0', min: '0'` 하드코딩(`Withdraw.tsx:109`)이며 스키마에 필드가 없다.

### 2. B-1 재정의 (§13)
Q1 답변은 **출금(debit) 경로**를 서술했을 뿐 **크레딧(credit) 경로**를 답하지 않았다.
B-1을 두 개로 분해한다:
- **B-0 (신규, 실질 최우선)**: 잔고 권위(balance authority)가 허브인가 BANA DB인가?
  → **마스터의 내부 결정 사항**이며 파트너 질의가 아니다.
- **B-1′**: (B-0 = 허브인 경우) 허브에 운영자→엔드유저 크레딧 수단이 있는가? → 파트너 질의 유지.

### 3. B-2 재정의 (§13)
- **B-2-i** (허브가 BANA를 자산으로 취급하는가): Q3 답변은 "추가하면 된다" = **오늘 확정 아님**.
  단 N-11에 의해 **코드로 즉시 반증 가능**하다 → 저비용 실증 절차를 §13에 명시.
- **B-2-ii** (허브측 트레저리 계정): Q4의 "admin 지갑 주소"는 **온체인 주소**를 가리키는 표현이며,
  허브 계정과 동일하지 않다. 리포지토리에 서명/전송 코드가 0건(전수 grep)이므로 이 지갑은
  **이 코드베이스에서 프로그래밍적으로 도달 불가능**하다. 미해소.

### 4. Q5 → 신규 제품 요구사항 (§8.7 신설 + §11.6 R-U27~R-U29)
"이체 수수료·최소 이체 단위를 admin에서 설정 가능해야 한다"를 요구사항으로 편입.
**중요 제약**: BANA 관리자 설정은 허브의 실제 네트워크 수수료를 **대체할 수 없다**(가산/상향만).
그리고 **계약 이자의 클레임에 수수료를 부과하는 것은 실질적 이율 인하**이므로 체결 시점 공시 +
포지션 스냅샷 대상이 된다(A1' 적용).

### 5. Q6/Q7 → PM 판정으로 종결 (§4.3 C-10/C-11 신설, B-2b 축소)
- **Q6(status 엔드포인트)**: 존재 여부에 **의존하지 않는 설계**를 채택. C-4(모호한 실패 → 재시도
  없이 FAILED + 수동 검토)가 이미 fail-closed이므로 status 엔드포인트는 운영 편의일 뿐 설계 입력이
  아니다. → **차단 해제**.
- **Q7(부분 성공)**: 상태기계에 **PARTIAL 상태를 만들지 않는다.** 허브가 보고한 크레딧 금액을
  신뢰해 부분 금액을 원장에 쓰는 것을 금지하고, 전액 성공 아니면 FAILED(수동 대사)로 종결.
  추가로 **1회 클레임 상한**을 두어 수동 대사 규모를 유한하게 만든다. → **차단 해제**.

### 6. §9 게이트 갱신
- G-0′를 **G-0″**로 재작성 (B-0 + B-1′ + B-2-i/ii).
- 게이트 요약 다이어그램에 B-0 선행 추가.

### 7. §13 / §13.1 / §14 갱신
- §13 표: B-1/B-2/B-2b → B-0/B-1′/B-2-i/B-2-ii/B-2b′로 재구성, 답변 반영 상태 컬럼 추가.
- §13.1 질의서: 7개 → **3개로 압축**하고 문장을 정밀화.
- §14: 순서 1을 "B-0 마스터 결정"으로 교체, "B-2-i 실증(코드로 확인 가능)" 항목 신규 삽입.

### 8. §16 미해결 질문 갱신
Q6/Q7 종결 반영, 잔고 권위 결정에 따른 파급 항목 추가.
