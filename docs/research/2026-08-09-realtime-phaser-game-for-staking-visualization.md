# What makes a real-time, Phaser-built 2D game (vs. a static progress-bar dashboard) — and how would that apply to a re-designed oil-drilling staking visualization?

Retrieved 2026-08-09. All sources listed at the bottom with retrieval date.

## Summary

"Feels like a real game" is not about visual richness alone — it requires a **persistent update/render loop** (something redrawing every frame independent of user input), **sprite-based objects with their own continuous motion/state** (not just numbers changing), and ideally **responsive polish** (particles, camera, tweened easing) layered on top; this is the design-literature concept of "game feel," and it is precisely what the rejected SVG-progress-bar version lacked. **Phaser 3** is well suited to this: its Scene owns its own update loop, GameObjects (Sprites, particle emitters) are first-class citizens of that loop, Arcade Physics gives cheap velocity/collision motion, and Tweens give easing/looping animation without needing physics at all — and there is an **official, actively promoted Phaser+Next.js template** (`phaserjs/template-nextjs`) built specifically around a React-wrapped `Phaser.Game` instance with an `EventBus` for cross-communication and `useEffect` mount/`game.destroy(true)` unmount cleanup, which is the standard integration pattern independently corroborated by multiple third-party tutorials. On the reference-game side, **Idle Miner Tycoon**, **Egg Inc**, and **Cookie Clicker** all share the same underlying visual trick regardless of genre label: they render a **persistently animated scene of characters/vehicles/objects that never fully stop moving**, on top of which numeric progression sits as a secondary, legible layer — and there is a distinct, named, precedented pattern ("ambient games" / passive virtual-pet sims like Neko Atsume) for a game where the player has **no direct moment-to-moment control** over the animated activity, which maps closely to BANA's fixed-term-deposit constraint. Performance-wise, a modest Phaser scene (a handful of tweened/animated sprites, Arcade Physics only, texture-atlased) is genuinely lightweight by every source consulted, and the Page Visibility API is the standard, well-documented mechanism for pausing/throttling the loop when the tab or canvas isn't visible — both directly answer the "can this coexist with serious financial UI" concern, though no source gives a hard, single-number FPS/battery benchmark for "10-20 sprites" specifically, so that figure is a reasoned synthesis, not a cited statistic (flagged below).

## Findings

### 1. What separates "a real 2D game" from a static progress-bar dashboard

- The core academic/design-literature concept here is **"game feel"** — Wikipedia's synthesis (itself citing Steve Swink's canonical *Game Feel* text) frames it around five components: **Input** (a natural control mapping), **Response** (low-latency reaction to input), **Context** (an environment that gives the mechanic something interesting to act on), **Polish** (particles, camera shake, vivid color, sound reinforcing impact), and **Metaphor** (matching player expectations of how the world should behave). None of these require "big graphics" — Super Mario Bros. is cited as exemplary because simple directional input becomes "complex, fluid, and deliberate" character movement, i.e., the *loop* and *response*, not asset fidelity, is what reads as "a game." · confidence: high · [en.wikipedia.org/wiki/Game_feel](https://en.wikipedia.org/wiki/Game_feel)
- Design-blog analysis of "why progress bars alone feel aimless" converges on the same point from the opposite direction: a screen that only shows accumulating bars/numbers, with no reactive animation, confetti, character feedback, sound, or camera response to state changes, is explicitly described as feeling "aimless" and lacking a sense of impact/consequence — this is effectively a description of BANA's rejected first attempt. The same sources note a real tension: too many bars/numbers *do* aid legibility but can undercut immersion, so the fix is not "remove the numbers" but "wrap the numbers in a persistently animated world." · confidence: medium (blog/UX sources, not peer-reviewed) · [cjleo.com/we-are-addicted-to-progress](https://cjleo.com/blog/we-are-addicted-to-progress/), [uxdesign.cc/from-rpgs-to-ux](https://uxdesign.cc/from-rpgs-to-ux-how-progress-indicators-affect-user-engagement-8748f02d766a)
- The practical minimum bar that recurs across every engine/game source in this report is: **(1)** a continuous update/render loop that runs independent of user input (not "redraw only on state change"), **(2)** sprite-based objects that have their own persistent motion or animation state (walk cycles, bobbing, particle streams) rather than only numeric labels changing, and **(3)** at least one layer of "polish" motion (tweened easing, particles, or camera movement) reacting to state changes. Interactivity and physics/collision are common but not strictly required — several of the reference titles below (Egg Inc, Idle Miner Tycoon's background scene) are largely non-interactive ambient animation with only occasional taps. · confidence: medium (synthesized across sources 1–4 above, not a single named source stating this exact checklist) · see sources above

### 2. Phaser 3 core concepts

- **Scene**: Phaser has no single global "world" object (a deliberate change from Phaser 2) — each Scene owns its own cameras, tweens, game objects, and display list, and runs its own lifecycle: `init()` → `preload()` → `create()` → then `update()` runs continuously every frame while the scene is in its `RUNNING` state, with rendering happening each frame alongside it. This *is* the persistent game loop referenced in Finding 1. · confidence: high (official docs) · [docs.phaser.io/phaser/concepts/scenes](https://docs.phaser.io/phaser/concepts/scenes)
- **GameObjects / Sprites**: created via a Scene's own factory (`this.add.sprite(...)`, `this.add.image(...)`), registering them into that Scene's update list and display list — objects are scoped to the Scene that created them, not global. · confidence: high · [docs.phaser.io/phaser/concepts/scenes](https://docs.phaser.io/phaser/concepts/scenes)
- **Tweens**: Phaser's Tween system animates arbitrary numeric properties (position, scale, alpha, rotation) over time with easing curves, independent of physics — this is the lightest-weight way to get continuous motion (e.g., a bobbing pump-jack, a pulsing glow, a looping walk-cycle path) without needing a physics body at all. · confidence: high (official API docs) · [photonstorm.github.io/Phaser.Tweens.Tween](https://photonstorm.github.io/phaser3-docs/Phaser.Tweens.Tween.html)
- **Arcade Physics**: a deliberately lightweight physics system ("meant for more 'arcade' or 'retro' style games") supporting only rectangle/circle (AABB) collision, plus velocity/acceleration/gravity/drag helpers. It must be explicitly enabled per-object (objects are not physics-enabled by default) and is explicitly positioned as fast/simple rather than realistic — appropriate for something like a truck driving back and forth or a worker walking a fixed path, not for anything requiring accurate rigid-body simulation. · confidence: high (official docs) · [docs.phaser.io/phaser/concepts/physics/arcade](https://docs.phaser.io/phaser/concepts/physics/arcade)
- **Particle Emitters**: a `ParticleEmitter` GameObject controls a pool of particles from a single controller (position, velocity, lifespan, texture) — the standard use case cited is fire/smoke effects, i.e., directly applicable to a drilling rig's steam/dust plume or a truck's exhaust puff. · confidence: high (official/API docs) · [docs.phaser.io/api-documentation/class/gameobjects-particles-particleemitter](https://docs.phaser.io/api-documentation/class/gameobjects-particles-particleemitter), [gamefromscratch.com/adventures-in-phaser-with-typescript-particles](https://gamefromscratch.com/adventures-in-phaser-with-typescript-particles/)
- **Scale Manager / responsive canvas**: Phaser's Scale Manager offers named modes — `FIT` (scales up/down to fit its container while preserving the original aspect ratio; documented as the mode "likely to be the most used" for most games), `RESIZE` (changes actual game dimensions to match the container, requiring in-game layout logic to re-align), and `EXPAND` (hybrid). For a game embedded in a fixed-size card/panel on a staking page (not full-viewport), `FIT` inside a sized parent `<div>` is the documented standard approach. · confidence: high (official docs, cross-confirmed by third-party writeups) · [docs.phaser.io/phaser/concepts/scale-manager](https://docs.phaser.io/phaser/concepts/scale-manager), [xjavascript.com/responsive-game-phaser-3](https://www.xjavascript.com/blog/how-to-create-a-responsive-game-for-any-screen-size-with-phaser-3/)

### 3. Phaser + React/Next.js integration pattern

- Phaser publishes an **official Next.js template** (`phaserjs/template-nextjs`), announced directly on phaser.io, built specifically to demonstrate React↔Phaser communication with TypeScript. It ships a `PhaserGame` React component that initializes and owns the `Phaser.Game` instance and exposes it (plus the currently active Scene) to the rest of the React tree via `forwardRef` (`phaserRef.current.game`, `phaserRef.current.scene`). · confidence: high (official Phaser source) · [phaser.io/news/official-phaser-3-and-nextjs-template](https://phaser.io/news/2024/03/official-phaser-3-and-nextjs-template), [github.com/phaserjs/template-nextjs](https://github.com/phaserjs/template-nextjs)
- Cross-communication uses a plain **EventBus** module: React calls `EventBus.emit('event-name', data)`, Phaser Scenes call `EventBus.on('event-name', handler)` (and vice-versa); a Scene is expected to emit a `"current-scene-ready"` event once it's initialized (or once it's finished waiting on an async call) so React knows the Scene reference is safe to use. For BANA this is the natural channel for "Scene reads real balance/term data passed down from the page" without the game needing its own data-fetching logic. · confidence: high (official template docs) · [github.com/phaserjs/template-nextjs](https://github.com/phaserjs/template-nextjs)
- Because Phaser touches `window`/`document` at import time, it **cannot be server-rendered**. The consistent, independently corroborated pattern (official template + multiple third-party tutorials) is: load the Phaser-wrapping component via `next/dynamic` with `{ ssr: false }`, keep it inside a `"use client"` component, and construct the `Phaser.Game` instance inside a `useEffect` — critically, **destroy it in the cleanup function** (`game.destroy(true); gameRef.current = null`) so navigating away or unmounting doesn't leak the WebGL/Canvas context or leave the render loop running. This directly answers the "don't drain the page hosting real financial UI" concern architecturally: proper unmount cleanup is a documented, standard requirement, not an edge case to discover later. · confidence: high (official template + independent tutorial converge) · [github.com/phaserjs/template-nextjs](https://github.com/phaserjs/template-nextjs), [generalistprogrammer.com/tutorials/phaser-nextjs-tutorial](https://generalistprogrammer.com/tutorials/phaser-nextjs-tutorial)
- Since BANA's App Router page is a Server Component for SEO/data and the game must be client-only, the documented split is: the page/route stays a normal Server Component; a small client "island" component wraps the dynamically-imported Phaser game and mounts inside whatever panel/card the page design allocates to it — this is compatible with "displayed immediately on the staking page" (no separate route) as long as that island is rendered directly in the page's JSX rather than behind a click-to-open modal/route. · confidence: medium (inferred from the documented dynamic-import pattern, not a source stating this exact scenario) · [generalistprogrammer.com/tutorials/phaser-nextjs-tutorial](https://generalistprogrammer.com/tutorials/phaser-nextjs-tutorial)

### 4. Real-time animated idle games — visual/animation approach specifically

- **Idle Miner Tycoon**: sources describe the visual approach as "cartoon-style," colorful and legible even at small screen sizes, with the concrete described animation loop being "miners tap away at the rock face, loading up resources that travel up an elevator and into a warehouse" — i.e., the mine, elevator, and warehouse are simultaneously animated, continuously-moving elements, not discrete before/after states. Concept-art portfolios from artists who worked on the title (miner skins, manager skins, event backgrounds) corroborate a dedicated character-art pipeline behind this, not a minimal placeholder art style. · confidence: medium (secondary description + artist portfolio, not the developer's own technical documentation) · [idleminertycoon.com](https://www.idleminertycoon.com/), [kennshinabery.myportfolio.com/sample-design-animation-idle-miner](https://kennshinabery.myportfolio.com/sample-design-animation-idle-miner)
- **Egg Inc**: reviewers consistently describe a persistent **"live 3D farm"** with "a moving chicken swarm" — as the farm grows, "shipping vehicles line up, hen houses fill with birds, and grain silos stack up," and better trucks/trains visibly "carry more eggs per trip." This is the clearest documented example of numeric progression (population, throughput, tier) being represented as *simultaneously* visible, continuously-animated scene elements rather than a separate stats screen. · confidence: medium (review/aggregator sources, not Auxbrain's own dev documentation) · [en.wikipedia.org/wiki/Egg,_Inc.](https://en.wikipedia.org/wiki/Egg,_Inc.), [play.google.com/egg-inc](https://play.google.com/store/apps/details?id=com.auxbrain.egginc&hl=en_US&gl=US)
- **Cookie Clicker**: even this famously "numbers going up" game layers continuous animation on top of the counter — clicking the Big Cookie triggers a scale-squash animation, a spawned particle (a small cookie graphic, replaced with dollar-bill particles during a seasonal event) and a floating/fading damage-number-style text, plus a background layer of cookies continuously falling/animating independent of clicks. This is cited as evidence that even the genre's most numbers-first example still relies on continuous particle/motion polish to avoid feeling inert. · confidence: medium (fan wiki, cross-referenced against two independent wiki mirrors) · [cookieclicker.fandom.com/wiki/Big_Cookie](https://cookieclicker.fandom.com/wiki/Big_Cookie), [cookieclicker.wiki.gg/wiki/Big_Cookie](https://cookieclicker.wiki.gg/wiki/Big_Cookie)
- **Idle factory-tycoon genre broadly** (Idle Car Factory Tycoon, Factory: Idle & Tycoon Game, Conveyor Idle, Idle Spinner Factory Builder): store-listing descriptions consistently describe continuously moving conveyor belts, "spinning cogs, sparks flying," trucks/forklifts moving cargo, and robotic arms operating — reinforcing that "things visibly, continuously operating" (not just numbers incrementing) is the genre-standard visual grammar, independent of theme. · confidence: low-medium (store-listing marketing copy only, not independently reviewed gameplay footage) · [mwm.ai/apps/factory-idle-tycoon-game](https://mwm.ai/apps/factory-idle-tycoon-game/6550902318), [crazygames.com/game/conveyor-idle](https://www.crazygames.com/game/conveyor-idle), [idlespinnerfactorybuilder.com](https://idlespinnerfactorybuilder.com/)
- **Oil-rig/oil-drilling-specific visual assets**: no game-industry writeup describing a specific title's pump-jack animation approach was found, but the motion-graphics/3D-asset marketplace confirms the pump jack's real-world motion is well-characterized and asset-available for reuse/reference: "the rhythmic up-and-down motion of its beam, walking beam, crank arm, and counterweights" is the standard rigged animation for this machine across multiple stock 3D marketplaces (Sketchfab, 3DOcean, Envato). This confirms the pump-jack's bobbing motion is a simple, well-defined, cheaply-animatable single-axis loop (rocking beam), not a complex simulation — a good sign for feasibility as a Phaser tween. · confidence: medium (asset-marketplace descriptions, not a games-industry source) · [elements.envato.com/oil-pump-jack-3d-outline](https://elements.envato.com/oil-pump-jack-3d-outline-HW8ZPE9), [sketchfab.com/oil-pumpjack-animated](https://sketchfab.com/3d-models/oil-pumpjack-animated-3-b1ca37376ee14f8b951be9e69a7baea8)

### 5. "Ambient" / low-agency simulation as a named, precedented design pattern

- **"Ambient games"** is a named academic term (Eyles, 2008, *International Journal of Computer Games Technology*) for games designed to be watched/run while the player is away or minimally interacting — described as "ignorable as it is interesting," with the player's role compared to "watching a conventional film... starts it playing and then watches the story unfold." This is the most directly relevant precedent for BANA's hard constraint (the player cannot change the real financial outcome and mostly watches). · confidence: medium (single peer-reviewed source found, not cross-verified against a second academic source) · [onlinelibrary.wiley.com/10.1155/2008/176056](https://onlinelibrary.wiley.com/doi/10.1155/2008/176056)
- **Neko Atsume** is the clearest mainstream, commercially successful example of this exact pattern in a virtual-pet/idle context: the player never directly controls a cat's moment-to-moment behavior — they set up an environment (food, toys, furniture) and cats "come to visit... stick around and play to their heart's content" on their own schedule/logic, entirely independent of direct player input in the moment. Sources describe it explicitly as "low-stress," "passive," and a departure from Tamagotchi-style games that require direct real-time care actions. This is a strong structural analog to "the player watches real background state (accrual, term progress) they cannot directly speed up or change." · confidence: medium (secondary/blog sources, converging across three independent write-ups) · [en.wikipedia.org/wiki/Neko_Atsume](https://en.wikipedia.org/wiki/Neko_Atsume), [medium.com/history-of-virtual-pets](https://medium.com/@metapals/a-brief-history-of-virtual-pets-from-tamagotchi-to-metapals-d5d4da1b5f28)
- Idle games generally are described in the same literature as sitting adjacent to (not identical to) ambient games: the player "occasionally engages in interactions like upgrades," distinguishing them from a pure ambient/observe-only design, but the *aesthetic* of "watch autonomous activity unfold, minimal direct control" is shared across both categories — supporting a hybrid framing (mostly-ambient scene, occasional legitimate real actions like "confirm new stake" or "claim matured term") rather than needing to pick one pure category. · confidence: medium · [onlinelibrary.wiley.com/10.1155/2008/176056](https://onlinelibrary.wiley.com/doi/10.1155/2008/176056)
- Standalone aquarium-simulator titles were also found as a second concrete reference cluster for the same pattern — described across multiple listings as designed for players to "watch fish drift," continuing "to evolve even when you're not actively playing," usable "as a virtual fish tank or screensaver" — reinforcing that a persistently-animated, low-agency scene is a viable, shipped, well-understood genre on its own (not just a theoretical pattern). · confidence: low-medium (app-store/itch.io listing descriptions, not independently reviewed) · [store.steampowered.com/Behind_Glass_Aquarium_Simulator](https://store.steampowered.com/app/1611580/Behind_Glass_Aquarium_Simulator/), [wadester1124.itch.io/aquarium-simulator](https://wadester1124.itch.io/aquarium-simulator/)

### 6. Performance/technical considerations for a persistent game loop next to financial UI

- `requestAnimationFrame` (the loop primitive Phaser/browsers use for animation) is **automatically throttled/paused by the browser itself in background/hidden tabs** specifically to protect performance and battery — this is stated as standard browser behavior, not something the app needs to reimplement from scratch, though it is still recommended to explicitly hook the **Page Visibility API** (`document.addEventListener('visibilitychange', ...)`, checking `document.hidden`) to pause or throttle the game deliberately, and to clamp/reset the first frame's delta-time on resume to avoid a large time-jump ("dt spike") after being backgrounded. This is the standard, documented mitigation for "don't drain battery when the tab isn't active." · confidence: high (MDN + multiple independent engineering write-ups converge) · [developer.mozilla.org/Page_Visibility_API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API), [developer.chrome.com/background_tabs](https://developer.chrome.com/blog/background_tabs), [fsjs.dev/beyond-basics-requestanimationframe-techniques](https://fsjs.dev/beyond-basics-requestanimationframe-techniques-game-development/)
- On the "is a modest scene actually heavy" question: no source gives a single authoritative number for "10-20 sprites," but the converging technical picture from Phaser's own performance guidance and independent optimization write-ups is that **a simple platformer/scene with under a few hundred sprites runs comfortably on Canvas rendering alone**, and that the standard high-impact mitigations (texture atlases to collapse many sprites into one draw call, Arcade Physics rather than Matter.js, disabling physics on off-screen objects, avoiding per-frame Tween churn) are what matters for cost — not raw sprite count at BANA's likely scale (a rig, a worker, a truck, a few particle emitters). A scene sized for this use case (rough estimate: 10-20 animated elements) is, by every source's stated thresholds, well within "lightweight," though this specific figure is this report's synthesis against those thresholds rather than a source's literal claim. · confidence: medium (synthesized from converging but non-identical sources; no source directly benchmarks a 10-20-sprite Phaser scene) · [freeblock.dev/browser-games-fps-battery](https://freeblock.dev/en/blog/raznoe/browser-games-how-to-avoid-killing-fps-and-battery-life), [generalistprogrammer.com/phaser-performance-optimization-guide](https://generalistprogrammer.com/tutorials/phaser-performance-optimization-guide), [github.com/phaserjs/phaser/blob/v3.60.0/changelog/3.60/MobilePerformance.md](https://github.com/phaserjs/phaser/blob/v3.60.0/changelog/3.60/MobilePerformance.md)
- Canvas rendering is explicitly flagged as CPU-bound, which "keeps a power-hungry core busy" under continuous animation and can be a real battery concern on mobile if the scene is pushed toward "hundreds of elements" — this is the ceiling case, not BANA's likely case, but is worth naming as the point at which "lightweight" stops being true. WebGL is the documented mitigation for scaling past that ceiling (hardware-accelerated, better for large sprite/effect counts) — Phaser 3 supports both renderers and can auto-select. Interestingly, one first-party GitHub issue and one third-party report both note **anecdotal cases where forcing Canvas mode outperformed WebGL on specific low-end/older mobile devices** (a Pixel 5 case cited a 30% FPS gain switching to Canvas) — i.e., "WebGL is always faster" is not universally true and renderer choice may need device-conditional testing rather than a fixed assumption. · confidence: medium (one anecdotal GitHub/blog report, not a controlled benchmark) · [github.com/phaserjs/phaser/issues/6989](https://github.com/phaserjs/phaser/issues/6989), [freeblock.dev](https://freeblock.dev/en/blog/raznoe/browser-games-how-to-avoid-killing-fps-and-battery-life)
- Cleanup-on-unmount (`game.destroy(true)` inside a `useEffect` return function) is the documented mechanism preventing a second, separately-running game instance/loop from accumulating if the user navigates away from and back to the staking page repeatedly — directly relevant since Next.js client-side navigation does not do a full page reload, so an un-cleaned-up Phaser instance would persist and stack. · confidence: high · [github.com/phaserjs/template-nextjs](https://github.com/phaserjs/template-nextjs), [generalistprogrammer.com/tutorials/phaser-nextjs-tutorial](https://generalistprogrammer.com/tutorials/phaser-nextjs-tutorial)

## Contradictions

1. **"WebGL is always the higher-performance choice for many sprites" vs. anecdotal reports of Canvas outperforming WebGL on specific low-end devices.** General optimization guidance (freeblock.dev, MoldStud) frames WebGL as the scalability answer once sprite/effect counts grow, but a first-party Phaser GitHub issue and an independent blog both report a case where switching *to* Canvas mode fixed a real performance regression on an older Android device. Neither position is authoritative for BANA's actual target devices; this should be device-tested rather than assumed, not resolved by research alone.
2. **Phaser Next.js template's own router structure is ambiguous across sources.** The GitHub README fetch (via WebFetch's summarization) described `src/pages/` and referenced `_document.tsx`, which reads like the Pages Router, while the official phaser.io announcement and this report's own knowledge of Phaser's later template releases suggest App Router support was added — the WebFetch summary itself flagged this as unconfirmed ("Router Approach... file-based routing... though specific App Router confirmation isn't provided in this excerpt"). This should be verified directly against the current `phaserjs/template-nextjs` repository structure before implementation, since BANA is on Next.js 15 App Router specifically.
3. **How "heavy" a persistent Phaser loop really is, at BANA's likely scale, is not directly benchmarked anywhere found** — sources converge on qualitative thresholds ("a few hundred sprites is fine on Canvas alone," "texture atlases matter more than raw count") but no source tested or reported numbers for a scene as small as BANA's likely use case (roughly 10-20 elements). The "genuinely lightweight" conclusion in the Summary is this report's reasoned inference from those thresholds, not a directly cited fact — flagged explicitly rather than presented as equally solid to the sourced claims above it.

## Synthesis — what a real-time Phaser version of the oil-drilling concept could plausibly look like

This section translates the findings above into concrete animation ideas, split by what is safe to represent as continuously moving/alive versus what must stay a static, discrete, real data point. This is a findings synthesis for `pm`/`game-planner` to evaluate — not a design decision, and not a claim that any of this is currently built or specified.

**Continuously animated / "alive" layer (decorative motion, not tied 1:1 to real financial state changing):**
- A **pump-jack sprite with a looping Tween** on its walking-beam rotation/vertical bob — per Finding 4's stock-3D-asset research, this is a well-defined single-axis rocking motion, cheap to represent as a 2-8 frame sprite-sheet loop or a pure Tween on a pivoted beam graphic, running continuously regardless of any real state (it signals "the rig is operating," not "your balance is growing right now").
- A **worker character walking a fixed patrol path** between wells/derricks (Arcade Physics velocity or a Tween along a path) — reinforces the "site is alive" read Egg Inc and Idle Miner Tycoon rely on, without implying any player action drove it.
- **Steam/dust/smoke particle emitters** at the rig top or truck exhaust, per Finding 2's particle-emitter capability — cheap, continuous, and a strong "polish" signal per the game-feel literature (Finding 1).
- A **truck that arrives/departs on a timer or tied to a real event** (e.g., the real daily-interest posting event, per the prior 2026-08-08 research doc's "server-time-anchored return-to-collect" finding) — this is the one piece of ambient motion that *could* legitimately be tied to a real event without implying the player caused it, since it dramatizes something that already happened on schedule, not something the player triggered.
- Background elements (birds, clouds, a day/night cycle, idle heat-shimmer) — pure atmosphere, zero data-binding, purely for the "never fully static" read.

**Static / discrete, must-not-imply-motion-or-growth-from-play layer (the real financial data points):**
- **Well/rig count** — should map 1:1 to actual distinct stakes/positions; a new rig should only appear when a real new stake is opened, never as a "reward" animation independent of a real deposit.
- **Deposit/principal amounts and accrued-interest figures** — per this repo's absolute rule 2 (decimal.js for all amounts) and the prior research doc's Finding 5/6, these numbers should be legible (barrel-fill-style container, per the 2026-08-08 doc) but must update **only** on real accrual/settlement events, never animate upward continuously in real time the way a slot-machine or number-ticker would, since that would visually imply the game is generating yield rather than displaying it.
- **Term/lock progress and maturity date** — a static or milestone-stepped indicator (not a smoothly animating progress fill that suggests the player is "speeding up" anything), consistent with the prior doc's flag against variable-ratio reward framing.
- **Any milestone/maturity celebration** — per the 2026-08-08 doc's Finding 7, this should be a fixed, predictable, threshold-based animation (term matured → one-time celebratory motion) rather than anything randomized in timing or size.

The dividing line, consistent with both this doc's Finding 5 (ambient-game pattern) and the constraint stated in the prompt, is: **motion that dramatizes "the site is operating in real time" is safe and is exactly what the genre's best examples do continuously; any motion that could be read as "your money is growing because of something happening on screen right now" is the line this design must not cross**, and that line-drawing is a `pm`/`game-planner` policy decision this report does not make.
