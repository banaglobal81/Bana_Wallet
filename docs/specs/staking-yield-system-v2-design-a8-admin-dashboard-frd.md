## 0. 요약 — 이 문서의 네 가지 판정

| # | 판정 | 요지 |
|---|------|------|
| **J-1** | **기존 부채 대시보드는 확장되는 것이 아니라 재배치된다** | 기존 화면의 데이터 원천(`StakePosition.paidInterest`)이 rev03 §5.4의 **삭제 대상**이다. 살아남는 것은 **원리**(DS-1/DS-2 판별자, E-1~E-5 3상태 분리, N-1~N-5 표기, S-1~S-7 위계, §7.7 금지어)이고, 죽는 것은 **필드와 화면 위치**다. 확장으로 쓰면 곧 지울 화면에 새 개념을 얹게 된다 → §3 |
| **J-2** | **모델 (C)에서 "클레임"은 부채를 갚지 않는다. 기존 대시보드의 `unpaidInterest` vs `hubSettled` 이분법이 그대로 이식되면 관리자가 부채를 과소평가한다** | 클레임은 **미청구 이자 → 로컬 잔고**의 내부 이동이다. 둘 다 회사 지갑에 대한 청구권이며 **둘 다 PoR-1′의 좌변**이다. 부채가 실제로 소멸하는 유일한 사건은 `WITHDRAWAL_EXECUTED` 차감(온체인 전송 검증 통과)이다 → §3.2 |
| **J-3** | **PoR-1′ 패널은 PASS/FAIL 2상태가 아니라 8상태다.** 그리고 **"검사한 적 없음"과 "PASS"가 같은 초록으로 렌더되는 순간 이 패널은 없느니만 못하다** | `NEVER_RUN / WORKER_OFF / STALE / QUERY_FAILED / INCOMPLETE / UNCONFIGURED / PASS / FAIL`. 특히 **UNCONFIGURED**(통제 주소 0건 상태에서 좌변도 0이라 산술적으로 PASS가 나오는 공허한 통과)를 PASS로 그리는 것을 금지한다 → §6.1 |
| **J-4** | **닫을 수 없는 인시던트 배너는 PoR-1′ FAIL과 T2에만 준다. T1은 주지 않는다** | T1(등재 감지)은 **선의의 파트너 행위로 발생할 수 있는 예상 가능한 사건**이며, 이것을 T2·PoR FAIL과 같은 로즈 배너에 넣으면 배너가 일상이 되고 진짜 위반이 묻힌다. rev03 §2.3이 X-3를 X-3′로 쪼갠 이유("한 번의 과잉 발동이 가드를 죽인다")를 **화면 층에도 그대로 적용**한다 → §8 |

**그리고 이 문서는 상위 문서에서 산술적 모순 하나를 발견했다** — A-3 §2.6의 PoR-1′ 좌변이
소프트 락 의미론(A-3 §1 원칙 2) 아래에서 **스테이킹 원금을 두 번 센다**. §2.2에서 정직하게
적고, §13-Q1으로 `pm`·`prisma-db-expert`에 되돌린다. 화면은 **어느 쪽으로 결론이 나든
올바르게 렌더되도록** 설계했다(§6.2의 `componentRole` + INV-P4).

## 1. Goal

관리자가 한 화면에서 다음 세 질문에 **추측 없이** 답할 수 있게 한다.

| 질문 | 답을 주는 요소 |
|------|----------------|
| **① 우리가 발행한 청구권 총액이 실제 보유 토큰을 넘었는가?** | PoR-1′ 패널(§6.1) — 좌변/우변/마진, 그리고 **"아직 판정할 수 없다"를 판정과 구분해서** |
| **② 그 청구권은 무엇으로 구성되어 있고, 어디까지가 확정 부채인가?** | 부채 구성 패널(§6.2) + 로컬 원장·홀드 패널(§6.3) |
| **③ 지금 무엇이 발행을 막고 있는가 / 막고 있지 않은가?** | 발행 게이트 패널(§6.5) + 권위 상태 패널(§6.6) |

**비목표(명시):**
- 부채를 **줄이는** 어떤 조작도 이 화면에 두지 않는다. 이 화면은 관측 표면이다. 유일한 예외는
  §6.4의 통제 주소 레지스트리이며, 그것도 **우변의 구성을 선언**할 뿐 금액을 입력하지 않는다.
- **준비금 수치를 사람이 입력하는 필드를 만들지 않는다**(§6.4 RG-5). 우변은 등록된 주소의
  온체인 조회 결과여야만 한다 — 손으로 적을 수 있는 준비금은 준비금 증명이 아니다.
- V2-BAND 지표 없음. 예약 풀(L-4)·노출 상한(L-3)·밴드 상품 관련 수치는 렌더하지 않는다.

### 2.2 이 문서가 발견한 문제 — PoR-1′ 좌변의 중복 계상 (escalation)

A-3 §2.6은 좌변을 개정 02 §4.2의 문장 그대로 옮겨 적었다:

```
Σ(로컬 원장 잔고) + Σ(USER_HUB 자금 원천 ACTIVE 원금) + Σ(미청구 이자) + Σ(그랜트 원금)
```

그런데 **같은 문서 §1 원칙 2 / §2.3이 스테이킹 원금을 "잔고를 바꾸지 않는 홀드"로 확정했다**(F-6/F-7).
소프트 락이면 사용자의 스테이킹 원금은 **이미 `UserCoinBalance.balance` 안에 들어 있다.**
따라서 첫 항과 둘째 항은 겹치고, 좌변은 원금을 **두 번 센다.**

- 개정 02 §4.2가 쓰였을 때 원금의 물리 형태는 미결정이었다(개정 02 §10-12가 그것을 열린 질문으로
  남겼다). A-3가 §11 Q15에 답하면서 **소프트 락을 확정**했지만, §2.6의 좌변 문장은 함께 갱신되지 않았다.
- **"보수적이니 안전하다"로 넘기지 않는다.** 과대 계상된 좌변은 준비금이 실제로 충분한 상황에서도
  FAIL을 만들고, FAIL이 상시화되면 운영자는 게이트를 끈다. 이것은 rev03 §2.3이 X-3를 쪼갠 이유와
  **정확히 같은 실패 양식**이다.

> **이 문서는 PoR-1′를 재정의하지 않는다** — 불변식의 소유자는 `pm`이다. 대신 두 가지를 한다.
> ① §13 Q1으로 escalate 한다. ② **어느 결론이 나오든 화면이 거짓말하지 않도록** 데이터 계약에
> `componentRole`(가산 항목 / 부분집합 항목)을 요구하고(§5 DC-6), 화면에 `Σ(가산 항목) == leftTotal`
> 불변식 검사(INV-P4, §8)를 넣는다. **서버가 중복 계상하면 화면이 그것을 드러낸다.**

### 2.3 이 문서가 발견한 두 번째 문제 — 실행 중 출금이 마진을 일시적으로 깎는다

LOCAL 레일 출금은 `AWAITING_ONCHAIN` 구간에서 **사람이 앱 밖에서 먼저 전송**하고 나중에 해시를
제출한다(A-5 §1.2). 그 사이:

- **우변**(회사 지갑 온체인 잔고)은 **이미 감소**했다.
- **좌변**은 그대로다 — 홀드는 잔고를 안 바꾸고(F-6), 차감은 검증 통과 시점에 일어난다(F-8).

즉 **마진이 출금액만큼 일시적으로 축소**되고, 마진이 얇으면 `FAIL`이 뜬다. 이것은 진짜 위반이
아니라 **타이밍 아티팩트**다. 매일 거짓으로 깨지는 불변식은 곧 무시되는 불변식이 된다는
rev03 §3.4의 경고가 여기에 그대로 적용된다.

> **화면 요구(PR-9).** 마진 옆에 **"실행 중 출금 합계(`AWAITING_ONCHAIN`)"** 를 **조정 항목으로
> 나란히** 표시한다. **불변식 계산을 몰래 보정하지 않는다** — 보정하면 실제 손실과 타이밍
> 아티팩트를 구분할 수 없게 된다. 화면이 두 숫자를 나란히 보여주고 판단은 사람이 한다.
> (PoR-1′ 자체가 이 항목을 흡수해야 하는지는 §13 Q2로 `pm`에 넘긴다.)

| §5.4 E-1~E-5 (로딩/실패/진짜 0의 3상태 분리, 실패 시 숫자 0건 렌더) | **전면 승계 · 확대.** 이 화면은 원천이 4개(권위/원장/부채/준비금)이므로 **섹션별로** 3상태를 갖는다 → §5 DC-2, §9 |

### 3.2 개념 매핑 — 기존 3숫자가 어디로 가는가 (요청 2의 핵심)

**기존 모델(지급 레일 없음)**

```
잠긴 원금(사용자 자금, 부채 아님)   |   미지급 이자(부채)   |   실지급 완료 = 0 (구조적)
```

**모델 (C) — 로컬 원장 + 온체인 준비금**

```
                    ┌─────────────── PoR-1′ 좌변 = 회사 지갑에 대한 청구권 총액 ───────────────┐
   로컬 잔고 총액          미청구 원장 이자        그랜트 원금(H-2-a인 경우)
   (= 클레임 완료분 +        (아직 클레임 안 됨)      (미발행 청구권)
      입금분 + …)
        │  ▲                      │                        │
        │  └────── 클레임 ────────┘                        │
        │        (부채 소멸 아님 — 버킷 이동)                │
        │                                                   │
        └── 출금 요청 → 홀드 → 온체인 전송 → 검증 → WITHDRAWAL_EXECUTED 차감
                                                       └── 여기서만 부채가 실제로 소멸한다
                    └──────────────────────────────────────────────────────────────────────┘
                                              ≤
                    Σ PlatformControlledAddress 온체인 BANA 잔고  (= 우변)
```

| 기존 개념 | (C)에서의 대응 | 주의 |
|---|---|---|
| `activePrincipal` | `activeUserFundedPrincipalTotal` | **LOCAL 코인에서는 로컬 잔고의 부분집합**(소프트 락, F-7). "사용자 자금이며 부채가 아니다"라는 기존 라벨은 **더 이상 성립하지 않는다** — 사용자가 로컬 원장에 맡긴 BANA는 회사 지갑이 실물로 들고 있어야 하는 청구권이다. 라벨 재작성 필수(§10) |
| `unpaidInterest` | `unclaimedLedgeredInterestTotal` | 이름의 "미지급"이 여전히 정확하다 |
| — (신규) | `localLedgerBalanceTotal` | **클레임 완료분이 여기 들어온다. 그리고 이것은 여전히 부채다** |
| `hubSettled` (= 0, `NO_RAIL`) | `onchainSettledTotal` (= `Σ WITHDRAWAL_EXECUTED`) + `withdrawalRailStatus` | **레일이 생겼으므로 구조적 0이 실측치가 된다.** DS-1이 지정한 "이 한 곳"의 교체 |
| `grantedActivePrincipal` (조건부 부채) | `grantPrincipalPayableTotal` | H-2 미결정이면 **`null`(= INCOMPLETE)**, `"0"`이 아니다 |
| — (신규) | 홀드 총액(사유별) | `WITHDRAWAL_PENDING` / `STAKE_PRINCIPAL_LOCK`. 잔고의 부분집합이며 **좌변에 더하지 않는다** |

> **J-2를 다시 강조한다.** 기존 화면은 "미지급 vs 지급 완료"라는 축 하나로 부채를 설명했고,
> 그 축은 지급 레일이 없다는 사실 덕분에 정확했다. (C)에서는 **클레임이 지급처럼 보이지만
> 지급이 아니다.** 만약 새 화면이 "미청구 이자"를 헤드라인에 두고 "클레임 완료"를 대비항으로
> 놓으면, 관리자는 클레임이 늘어날수록 부채가 줄어든다고 읽는다. **실제로는 부채 총액이
> 1원도 변하지 않는다.**
> → 요구 **LB-1**: 부채 패널의 헤드라인은 `unclaimedLedgeredInterestTotal`이 아니라
> **좌변 총액(`leftTotal`)** 이다. 클레임 관련 수치는 그 **내부 분해**로만 나타난다.

## 4. 정보 구조 — 어디에 두는가

### 4.1 신규 페이지 `/admin/reserve` (경로명 제안)

**`/admin/staking` 안에 넣지 않는다.** 근거는 F-16이다: 준비금 좌변은 스테이킹 이자·그랜트
원금·레퍼럴·보상 플랜을 **모두** 포함하며, 개정 02 §4.4가 *"G-3′는 v2보다 상위의 재무 과제"* 라고
못 박았다. 이것을 스테이킹 하위 화면에 두면 **"준비금은 스테이킹 문제"라는 틀린 프레임을
화면 구조가 가르친다.** 그리고 `/admin/staking`은 삭제 대상이다(F-17).

```
/admin/reserve  (신규 · 관리자 사이드바 1급 항목)
├─ 【0】 인시던트 배너 (조건부 · 닫기 불가)              ← §8
├─ 【1】 T1 경고 밴드 (조건부 · 닫기 불가 · 인시던트 아님) ← §8
├─ 【2】 PoR-1′ 준비금 검증 패널       (코인별)          ← §6.1  ★요청 1
├─ 【3】 부채 구성 패널                (코인별)          ← §6.2  ★요청 2
├─ 【4】 로컬 원장·홀드 패널           (코인별)          ← §6.3  ★요청 2
├─ 【5】 발행 게이트 패널              (코인별)          ← §6.5
├─ 【6】 권위 상태 패널                (코인별)          ← §6.6  ★요청 3
├─ 【7】 통제 주소 레지스트리          (코인×네트워크)   ← §6.4
└─ 【8】 검증 실행 이력                (코인별 · 최근 N) ← §6.7
```

**순서 근거:** 관리자가 이 화면을 여는 이유는 대부분 "지금 괜찮은가"이다. 판정(【2】)이
구성(【3】【4】)보다 위에 있어야 하고, "왜 막혔는가"(【5】【6】)가 그 다음이다. 레지스트리와
이력은 조작·감사용이므로 아래로 내린다.

**코인 처리:** 코인 1개당 1블록. **코인 간 합계 행을 만들지 않는다**(기존 FRD §4.2 승계, 그리고
X-2/F-14가 이것을 불변식 수준으로 요구한다). 오늘 LOCAL 권위 코인은 BANA 하나(F-15)이지만,
합계 행이 있으면 코인이 늘어나는 순간 틀린 숫자가 된다.

**HUB 권위 코인의 처리:** 이 페이지는 **LOCAL 권위 코인만** 다룬다. HUB 코인은 로컬 원장도
준비금 개념도 없으므로 렌더 대상이 아니다. 단 §6.6 권위 패널만은 **전 코인**을 대상으로 한다 —
"HUB 코인인데 로컬 잔고 행이 존재한다"는 것이 그 자체로 버그이기 때문이다(A-3 §2.1 주석).

## 5. 데이터 계약 — `GET /api/admin/solvency` (엔드포인트명 제안)

### 5.1 왜 단일 엔드포인트 + 섹션별 상태 봉투인가

원천이 4종(권위·로컬 원장·부채·준비금)이고 각각 실패할 수 있다. 선택지는 둘이었다.

- **엔드포인트 4개** — 부분 실패가 자연스럽게 표현되지만, 화면이 4개의 로딩/에러 상태를
  조합해야 하고 **"전부 성공한 것처럼 보이는 부분 성공"** 이 생기기 쉽다.
- **엔드포인트 1개 + 섹션별 판별자** — 부분 실패를 **와이어 포맷이 강제**한다. 채택.

> **요구 DC-1.** 응답은 코인별 객체 배열이며, 각 섹션은 **판별 유니온**이다.
> `{ status: 'OK', ... } | { status: 'UNAVAILABLE', reason: string }`.
> **어떤 섹션도 실패를 빈 값·0·`null` 데이터로 표현하지 않는다.**
>
> **요구 DC-2.** 한 섹션의 `UNAVAILABLE`이 다른 섹션의 렌더를 막지 않는다. 그리고
> **`UNAVAILABLE` 섹션의 자리에 숫자를 렌더하지 않는다**(기존 FRD E-2/E-3 승계).
>
> **요구 DC-3. 전체 요약 판정("정상")을 서버가 만들지 않는다.** 섹션 하나라도 `UNAVAILABLE`이면
> 그 코인에 대한 어떤 종합 초록불도 존재해서는 안 된다. 판정은 §6.1의 PoR 상태 하나뿐이며,
> 그것은 준비금에 대한 판정이지 시스템 전반에 대한 판정이 아니다.

### 5.2 응답 형태 (개념 초안 — 필드명은 제안)

```ts
interface AdminSolvencyCoin {
  coin: string;                                  // "BANA"
  authority: 'HUB' | 'LOCAL';                    // A-2 getCoinAuthority()

  reserve:      Section<ReserveSection>;         // §6.1  PoR-1′
  liability:    Section<LiabilitySection>;       // §6.2
  localLedger:  Section<LocalLedgerSection>;     // §6.3
  issuanceGate: Section<IssuanceGateSection>;    // §6.5
  authorityWatch: Section<AuthorityWatchSection>;// §6.6
}

type Section<T> = ({ status: 'OK' } & T) | { status: 'UNAVAILABLE'; reason: string };

interface ReserveSection {
  // 최신 ReserveVerificationRun. 한 건도 없으면 null — "PASS 아님"이지 "실패"도 아니다.
  latestRun: {
    id: string;
    ranAt: string;                     // ISO
    trigger: 'WORKER_PERIODIC' | 'MANUAL_ADMIN' | 'PRE_AUTHORITY_TRANSITION' | 'PRE_ISSUANCE_GATE';
    result: 'PASS' | 'FAIL' | 'INCOMPLETE' | 'QUERY_FAILED';
    leftTotal: string | null;          // null = 계산 불가 (A-3 원칙 5)
    rightTotal: string;                // controlledOnchainBalanceTotal
    marginAmount: string | null;       // right − left. 음수 = 위반
    breachDetail: string | null;
    blocksIssuance: boolean;
    controlledAddressCount: number;    // 실행 시점의 active 주소 수
    components: ReserveComponent[];    // DC-6
  } | null;

  // DC-4 — 상태 판정에 필요한 부수 사실. 클라이언트가 시각을 계산해 유추하지 않는다.
  workerEnabled: boolean;              // PlatformSetting.porVerificationWorkerEnabled
  intervalMinutes: number;             // porVerificationIntervalMinutes
  staleAfterMinutes: number;           // DC-5
  isStale: boolean;                    // 서버가 판정한다
  consecutiveQueryFailedCount: number; // X-6과 같은 결의 에스컬레이션 근거
  activeControlledAddressCount: number;// "지금" 등록되어 있는 수 (latestRun 시점과 다를 수 있다)

  // §2.3 — 타이밍 아티팩트 조정 항목. 좌변/우변 어디에도 합산되지 않는다.
  inFlightOnchainWithdrawalTotal: string | null;  // Σ amount WHERE status='AWAITING_ONCHAIN'
}

interface ReserveComponent {
  key: 'localLedgerBalanceTotal' | 'activeUserFundedPrincipalTotal'
     | 'unclaimedLedgeredInterestTotal' | 'grantPrincipalPayableTotal';
  amount: string | null;               // null = 계산 불가
  role: 'ADDITIVE' | 'SUBSET_OF_LOCAL_BALANCE';   // DC-6
  blockedBy: 'A4_NOT_SHIPPED' | 'H2_UNDECIDED' | null;  // null이면 계산됨
}
```

> **요구 DC-4. 상태 판정은 서버가 한다.** `isStale`, `consecutiveQueryFailedCount`,

## 6. 화면 — `/admin/reserve`

### 6.1 【2】 PoR-1′ 준비금 검증 패널 (요청 1)

#### 6.1.1 상태 기계 — 8상태와 렌더 우선순위

> **요구 PR-1. 패널은 `result` 4값을 그대로 그리지 않는다.** `result`에 **부수 사실**
> (실행 이력 유무 · 워커 on/off · 신선도 · 주소 등록 수)을 결합해 **8개의 표시 상태** 중
> 하나를 고른다. 아래 우선순위로 **위에서부터 첫 번째로 일치하는 것**이 표시 상태다.

| # | 표시 상태 | 조건 | 색/톤 | 인시던트? |
|---|---|---|---|---|
| 1 | **`FAIL`** | `latestRun.result === 'FAIL'` | 로즈 | **예**(§8 INC-P1) |
| 2 | **`NEVER_RUN`** | `latestRun === null` | 중립 회색 | 아니오 |
| 3 | **`QUERY_FAILED`** | `latestRun.result === 'QUERY_FAILED'` | 앰버 | 조건부(연속 N회 시 §8 INC-P5) |
| 4 | **`STALE`** | `isStale === true` (결과값 무관) | 앰버 | 조건부(§8 INC-P4) |
| 5 | **`INCOMPLETE`** | `latestRun.result === 'INCOMPLETE'` | 중립 회색 | 아니오(단 발행 ON이면 §8 INC-P3) |
| 6 | **`UNCONFIGURED`** | `result === 'PASS'` **그리고** `latestRun.controlledAddressCount === 0` | 중립 회색 | 아니오 |
| 7 | **`PASS`** | 위 어디에도 해당 없음 | **에메랄드**(§6.1.4 예외) | 아니오 |
| 8 | **`UNAVAILABLE`** | 섹션 자체가 `UNAVAILABLE` | 로즈 테두리 · 숫자 0건 | 아니오 |

**부수 칩(표시 상태와 별개로 항상 표시):**
- `workerEnabled === false` → **"검증 워커 꺼짐"** 칩. 이것이 `NEVER_RUN`/`STALE`의 **원인**임을
  같은 줄에서 알 수 있어야 한다.
- `isStale === true` 이고 표시 상태가 `FAIL`인 경우 → **"오래된 판정"** 칩(FAIL이 우선하되,
  그 FAIL이 언제 것인지 숨기지 않는다).
- `activeControlledAddressCount !== latestRun.controlledAddressCount` → **"주소 구성 변경됨"** 칩
  (§6.4 RG-6).

#### 6.1.2 각 상태의 판정 근거

| 상태 | 왜 이 상태를 따로 두는가 |
|---|---|
| **`NEVER_RUN`** | 검사 이력이 0건인 것은 "통과"가 아니다. 그런데 `result` enum에는 이 값이 없으므로 **화면이 만들지 않으면 존재하지 않는 상태**가 된다. 초기 배포 직후 전 코인이 이 상태이며, 이때 초록이 뜨면 그 스크린샷이 남는다 |
| **`WORKER_OFF`**(칩) | 워커를 끄면 `latestRun`이 영원히 그대로 남는다. 즉 **PASS가 화석화된다.** 상태를 별도로 만들지 않고 칩으로 두는 이유는, 워커가 꺼진 채로도 최근 수동 실행이 있을 수 있어 `STALE`과 조합이 필요하기 때문이다 |
| **`STALE`** | 마지막 판정이 참이었더라도 그것은 그 시점의 사실이다. 개정 03 N-23이 *"이것은 시점 관측이며 전제로 코드를 쓰지 말 것"* 이라고 한 것과 같은 원리를 **화면 층에 적용**한 것이다 |
| **`QUERY_FAILED`** | A-3 §2.6이 명시한 대로 **장애이지 판정이 아니다.** FAIL로 그리면 실제 위반과 구분이 사라지고, PASS로 그리면 조회 못 한 것을 통과라고 말하게 된다 |
| **`INCOMPLETE`** | F-4에 따라 **H-2 결정 전까지는 이것이 정상 상태**다. 오류처럼 그리면 운영자가 매일 고치려 들다가 무시하게 된다. 오류가 아니라 **"아직 답이 없는 질문이 남아 있다"** 로 그린다 |
| **`UNCONFIGURED`** | **이 문서에서 가장 중요한 신규 상태.** 통제 주소가 0건이면 우변은 정직하게 0이고(F-3), 좌변도 0이면(오늘의 프로덕션 — F-15) `0 ≤ 0`이 성립해 **`result = PASS`가 나온다.** 이 PASS는 아무것도 증명하지 않는다. 초록으로 그리는 순간 화면이 "준비금 검증 통과"라고 거짓말한다 |

| **LB-5** | `onchainSettledTotal`에는 **"실제로 소멸한 부채"** 라는 의미가 라벨에 들어가야 한다. 이 값 옆에 `withdrawalRailStatus` 판별자 배지를 단다(`NO_RAIL` → "출금 레일 없음", `MANUAL_ONCHAIN` → "수동 온체인 레일") — DS-2 패턴 승계 |
| **LB-6** | **클레임 완료 누계를 "지급"으로 읽히는 위치에 두지 않는다.** 클레임은 로컬 잔고 증가로만 나타나며, 별도의 "클레임 완료" 헤드라인 수치를 만들지 않는다(J-2) |
| **LB-7** | `claimRailStatus`는 **상태 칩**이지 액션이 아니다. 이 화면에서 킬 스위치를 토글하지 않는다(관측 표면 원칙 §1 비목표) |
| **LB-8** | `dailyAccrualRate`는 기존 FRD §5.1 그대로 — 카드 안 한 줄. `null`이면 LB-4 적용 |

### 6.3 【4】 로컬 원장·홀드 패널 (요청 2 — 신규 개념)

| ID | 요구 |
|----|------|
| **LL-1** | **`balance` / `held` / `available` 세 숫자를 항상 별개 항목으로** 표시한다. 어떤 둘도 합치지 않는다(개정 01 R-U1의 관리자판, 기존 FRD S-2 승계) |
| **LL-2** | **홀드는 사유별로 분해**한다. `WITHDRAWAL_PENDING`과 `STAKE_PRINCIPAL_LOCK`은 성격이 정반대다 — 전자는 곧 나갈 돈이고 후자는 나가지 않을 돈이다. 합계만 보여주면 운영자가 유출 예정액을 과대평가한다 |
| **LL-3** | **`STAKE_PRINCIPAL_LOCK` 옆에 "소프트 락 · 잔고에서 차감되지 않음"** 캡션을 고정으로 단다(F-6/F-7). 이 캡션이 없으면 §2.2의 중복 계상 오해가 화면에서 재생산된다 |
| **LL-4** | **홀드 총액을 청구권 총액(`leftTotal`)에 더하지 않는다.** 홀드는 잔고의 부분집합이다 |
| **LL-5** | 대사 결과: `mismatchCount > 0` 또는 `versionDriftCount > 0`이면 §8 INC-L1/INC-L2 인시던트가 함께 뜬다. **패널 안에서 조용히 숫자만 보여주고 끝내지 않는다** |
| **LL-6** | `reconciliation.lastRunAt === null`이면 **"미대사"** 로 표시한다. `불일치 0`으로 표시하지 않는다 — 검사한 적 없음은 통과가 아니다(PR-1과 같은 원리) |
| **LL-7** | 대사 실행 시각도 PR-7(절대+상대) 적용. 그리고 **오래된 대사는 "불일치 0"과 함께 신선도 칩을 단다** |
| **LL-8** | `holdInvariant.matches === false`면 두 숫자를 **나란히 표시하고 차액을 함께** 보여준다. 어느 쪽이 큰지가 진단의 절반이다 |
| **LL-9** | **권위가 `HUB`인 코인에 로컬 원장 섹션이 `status: 'OK'`로 오면 그 자체가 인시던트다**(§8 INC-A3). A-3 §2.1 주석이 *"HUB 권위 코인에 이 테이블 행이 있는 것은 버그"* 라고 명시했다 |
| **LL-10** | **X-2 준수: 이 패널에 허브 잔고를 함께 표시하지 않는다.** 나란히 두는 것만으로도 합산 유혹이 생긴다 |

### 6.4 【7】 통제 주소 레지스트리 (PoR-1′ 우변의 구성)

준비금 우변은 **관리되는 데이터**여야 한다(rev03 §3.4 DP-6 / A-3 §1 원칙 6). 그 데이터를
입력·검수하는 유일한 화면이다.

| ID | 요구 |
|----|------|
| **RG-1** | 목록: 코인 · 네트워크 · 주소(전문, 말줄임 금지 · 복사 버튼) · 라벨 · 활성 여부 · 등록자/등록 시각 · 비고 |
| **RG-2** | **각 주소에 블록 익스플로러 링크를 렌더한다.** 공개 검증 가능성이 (C)를 채택할 유일한 적극적 이유였다(개정 02 §4.2). 링크가 없으면 그 성질이 화면에서 사라진다 |
| **RG-3** | 추가 시: 코인·네트워크·주소·라벨을 요구하고, **주소 형식 검증 + 중복 검증**(`@@unique([coin, network, address])`)을 입력 단계에서 수행한다 |
| **RG-4** | **삭제는 하드 삭제가 아니라 `active=false` + `removedAt`이다.** 과거 검사 실행의 우변이 무엇으로 구성됐는지가 사후에도 재구성 가능해야 한다 |
| **RG-5** | **준비금 금액을 사람이 입력하는 필드를 만들지 않는다.** 우변은 등록 주소의 온체인 조회 결과뿐이다. "수동 준비금 보정" 같은 필드가 생기면 PoR-1′는 그 순간 자기 신고가 된다 |
| **RG-6** | **추가/비활성화는 우변을 즉시 바꾼다.** 화면은 변경 전에 *"이 변경은 다음 검사부터 준비금 합계에 반영됩니다"* 를 고지하고, 변경 후 **활성 주소 수가 최근 실행 시점과 달라졌음**을 §6.1의 칩으로 드러낸다 |
| **RG-7** | 모든 추가·비활성화는 `AuditLog`에 남는다(누가·언제·어떤 주소·이전 상태→새 상태). A-3의 `addedByAdminId`/`addedByEmail`이 있으나 **변경 이력은 AuditLog가 맡는다**(A-2 §2.4의 판단과 같은 결) |
| **RG-8** | **활성 주소가 0건이면 목록 상단에 상시 안내**를 띄운다: *"통제 주소가 등록되지 않아 준비금 검증이 성립하지 않습니다(Q-M3 미회신)."* 빈 표로 두면 "아직 안 만든 화면"처럼 보인다 |

## 8. 불변식과 인시던트 배너 판정 (요청 4)

### 8.1 판정

> **닫을 수 없는 로즈 인시던트 배너는 "지금 자금이 위험하거나, 자금이 안전하다는 주장의 근거가
> 무너졌다"에만 준다. 그 밖의 모든 비정상은 패널 내 상태이거나 별도의 앰버 경고 밴드다.**

| 조건 | 취급 | 근거 |
|---|---|---|
| **PoR-1′ `FAIL`** | **로즈 인시던트 · 닫기 불가** | 발행된 청구권이 준비금을 넘었다. 개정 02 §4가 *"PoR-1이 유일한 방어선"* 이라고 한 그 방어선이 깨진 상태 |
| **권위 T2(`T2_HALTED`)** | **로즈 인시던트 · 닫기 불가** | X-1′ 위반 확정 + fail-closed 발동. 모델 (C)를 안전하게 만드는 **유일한 성질**이 깨졌다(개정 02 P-1). 그리고 발행·체결·출금이 멈춘 상태를 운영자가 모르면 장애 대응이 시작되지 않는다 |
| **로컬 원장 대사 불일치**(`mismatchCount > 0`) | **로즈 인시던트 · 닫기 불가** | 캐시와 증거가 어긋났다 = 화면의 모든 로컬 잔고 수치를 신뢰할 수 없다. A-3 §4.4가 자동 정정을 금지했으므로 **사람이 봐야만 해소된다** |
| **버전 드리프트**(`versionDriftCount > 0`) | **로즈 인시던트 · 닫기 불가** | 공유 함수를 우회해 `UserCoinBalance`를 직접 수정한 코드 경로가 존재한다는 뜻(F-10). 원장 무결성의 근본 전제가 깨진 것 |
| **홀드 불변식 위반**(`holdInvariant.matches === false`) | **로즈 인시던트 · 닫기 불가** | W-2 불변식. 홀드와 미결 요청이 어긋나면 초과 인출 또는 잠긴 자금 유실 중 하나다 |
| **발행이 켜져 있는데 PoR이 PASS가 아님** | **로즈 인시던트 · 닫기 불가** | "검증 없이 발행 중"이다. 개정 02 §4.2가 요구한 fail-closed가 실제로는 걸려 있지 않다는 뜻 |
| **HUB 권위 코인에 로컬 잔고 존재** | **로즈 인시던트 · 닫기 불가** | X-1′의 역방향 위반(LL-9) |
| **연속 `QUERY_FAILED` N회 이상** | **로즈 인시던트 · 닫기 불가**(N 도달 전에는 패널 내 앰버) | X-6의 "N회 연속 UNKNOWN → T1 승격"과 **같은 설계 언어**. 판정 불가가 장기화되면 그것 자체가 사고다 |
| **`STALE`이 오래 지속**(제안: `staleAfterMinutes` × 4) | **로즈 인시던트 · 닫기 불가** | 검증 워커가 죽었는데 마지막 PASS가 화석으로 남아 있는 상태 |
| **권위 T1(`T1_WARNING`)** | ❌ 인시던트 아님 · **별도 앰버 경고 밴드 · 닫기 불가** | **§8.2** |
| **PoR `INCOMPLETE` / `NEVER_RUN` / `UNCONFIGURED`** | ❌ 인시던트 아님 · 패널 내 상태 | F-4에 따라 **오늘의 정상 상태**다. 배너로 올리면 배포 첫날부터 상시 점등되어 배너가 죽는다. 단 "발행 ON"과 결합하면 위 항목으로 격상된다 |
| **PoR `QUERY_FAILED` 단발 / `STALE` 단기** | ❌ 인시던트 아님 · 패널 내 앰버 | 일시 장애와 사고를 구분한다(A-5 §2.5의 실패 사유 분류와 같은 원리) |
| **워커 OFF** | ❌ 인시던트 아님 · 칩 | 의도적 운영 조치일 수 있다. 단 STALE로 이어지면 위 항목으로 자연히 격상된다 |
| **`TX_ALREADY_CONSUMED` 발생**(A-5 §2.5) | **로즈 인시던트 권고 — 단 A-5 데이터 계약 필요** | A-5가 *"관리자 실수 또는 의도적 재사용 시도"* 로 분류하며 표준보다 높은 심각도를 권고했다. 이 문서는 **인시던트 대상으로 편입할 것을 권고**하되, 집계 계약이 A-5 구현에 달려 있으므로 **P2**로 둔다(§11) |

### 8.2 T1을 인시던트로 만들지 않는 이유 (요청 4의 핵심)

1. **T1은 예상 가능한 정상 사건이다.** 마스터가 Q-M1에서 *"허브에도 등록되어 있을 수 있다"* 고
   답했고(rev03 §2.1), 그것이 X-1을 X-1′로 다시 쓰게 만든 이유다. **파트너가 선의로 목록에
   BANA를 추가하는 날 T1이 뜬다.** 그날 사용자 자금은 아무 문제가 없다.
2. **rev03 §2.3이 이미 같은 판단을 코드 층에서 내렸다.** X-3를 X-3′로 쪼갠 이유가
   *"한 번의 과잉 발동이 가드를 죽인다"* 였다. **그 논리를 화면 층에서만 뒤집을 이유가 없다.**
   T1을 T2·PoR FAIL과 같은 로즈 배너에 넣으면, 로즈 배너가 "가끔 뜨는 것"이 되고 진짜 위반이
   묻힌다. 이것은 화면판 과잉 발동이다.
3. **그러나 T1은 무시해도 되는 것도 아니다.** 신규 발행이 차단되고 프로브 주기가 상향된다(F-11).
   그래서 **닫을 수 없는 앰버 경고 밴드**라는 중간 등급을 만든다 — 인시던트 배너 바로 아래,
   페이지 상단 고정, 닫기 없음, 그러나 색과 문구가 "지금 사고 중"이라고 말하지 않는다.

> **요구 IN-1. 로즈(인시던트)와 앰버(경고)는 서로의 자리를 침범하지 않는다.**
> 인시던트 배너에 앰버 항목을 섞지 않고, 앰버 밴드에 로즈 항목을 섞지 않는다.

### 8.3 배너 요구사항

| ID | 요구 |
|----|------|
| **IN-1** | 로즈 인시던트 배너 / 앰버 T1 경고 밴드는 **별개 컴포넌트**다(§8.2) |
| **IN-2** | 둘 다 **닫기 버튼이 없다.** 기존 FRD §5.5의 결정을 승계 |
| **IN-3** | 인시던트가 여러 건이면 **전부 렌더**한다. "외 N건"으로 접지 않는다. 접는 순간 두 번째 인시던트는 없는 것이 된다 |
| **IN-4** | 각 인시던트는 **① 무엇이 깨졌는지 ② 그 결과 무엇을 신뢰할 수 없는지 ③ 무엇을 하지 말아야 하는지**를 말한다. 기존 FRD §7.3 `paidStatus` 문구가 이 3요소 구조의 견본이다 |
| **IN-5** | **인시던트 판정은 서버에서 한다.** 대사 결과·프로브 이력은 DB 없이 판정 불가이고, 세 화면(리저브·스테이킹·대시보드)이 각자 판정하면 갈라진다. 기존 `detectLiabilityIncidents`(클라이언트 유도)는 **폐기**한다(§3.3) |
| **IN-6** | **클라이언트가 모르는 `code`를 받으면 무시하지 않는다.** 알 수 없는 코드는 *"알 수 없는 인시던트 코드 {code} — 배포 버전 불일치일 수 있습니다"* 로 렌더한다. 조용히 드롭하면 **새 인시던트를 추가한 날 그 인시던트만 화면에서 사라진다** |
| **IN-7** | 배너는 **인시던트 발생 코인과 관련 실행 ID(`runId`)를 명시**한다. 코인이 여럿일 때 어느 코인인지 모르면 조치할 수 없다 |
| **IN-8** | 인시던트 배너 렌더는 **섹션 로딩과 무관**하다. 인시던트 데이터가 도착하면 즉시 렌더하고, 다른 섹션의 로딩을 기다리지 않는다 |

## 9. 상태·에러 경로 전수 (기존 FRD §5.4 E-1~E-5의 확장)

각 패널은 아래 상태를 **전부** 구현한다. 이 표에 없는 렌더는 만들지 않는다.

| 상태 | 트리거 | 렌더 | 금지 |
|---|---|---|---|
| **로딩** | 최초 fetch 진행 중 | 스켈레톤 또는 `—` | **숫자 렌더 금지**(E-3) |
| **섹션 실패** | `section.status === 'UNAVAILABLE'` | 로즈 테두리 에러 카드 + `reason` + 다시 시도 | **숫자 0건.** 특히 `0` 금지(E-2) |
| **전체 실패** | 엔드포인트 자체 실패 | 페이지 상단 에러 카드 + *"이 공백을 '부채 0' 또는 '준비금 정상'으로 해석하지 마십시오"* | 빈 페이지 |
| **값 없음(진짜)** | LOCAL 권위 코인이 0개 | *"로컬 권위 코인이 없습니다"* 명시 | 섹션 숨김 |
| **구성요소 계산 불가** | `amount === null` | 사유 문구(PR-4/LB-4) | `0` 대체, 행 숨김 |
| **검사 이력 없음** | `latestRun === null` | `NEVER_RUN` | `PASS`, 초록 |
| **판정 오래됨** | `isStale` | `STALE` + 시각 | 최근 결과를 현재 결과로 렌더 |
| **권한 없음** | 401/403 | 기존 관리자 라우트 패턴 준수 | — |

| ID | 요구 |
|----|------|
| **E-1′** | `.catch(() => [])` / `.catch(() => null)` 로 실패를 데이터로 바꾸지 않는다. 실패는 실패로 보관한다 |
| **E-2′** | **실패 섹션 옆의 성공 섹션은 정상 렌더한다.** 한 섹션 실패가 페이지를 비우지 않는다 |
| **E-3′** | **부분 실패 상태에서 어떤 종합 초록불도 렌더하지 않는다**(DC-3) |
| **E-4′** | 다시 시도는 **실패한 섹션만** 재조회하지 않고 엔드포인트 전체를 재조회한다(단일 엔드포인트이므로). 부분 갱신으로 섹션 간 시점이 어긋나는 것을 만들지 않는다 |
| **E-5′** | 자동 폴링을 넣는다면 주기는 `intervalMinutes`와 **독립적으로** 정하되, 폴링 실패가 화면의 마지막 성공 값을 조용히 유지하지 않는다 — **"마지막 갱신 시각"을 항상 표시**한다 |

## 14. 이 문서가 승인하지 않는 것 (명시)

- **구현 착수 승인이 아니다.** 이 화면은 A-2/A-3 마이그레이션에 의존하고, 그 실행은
  rev03 §7.2의 3조건에 막혀 있다.
- **PoR-1′ 불변식의 재정의가 아니다.** §2.2/§2.3은 **문제 제기**이며, 판정은 `pm` 소관이다.
- **발행 게이팅 배선의 승인이 아니다.** `ReserveVerificationRun.blocksIssuance`를 실제로
  발행을 막는 코드에 연결하는 작업은 A-5/A-10 소관이며(A-3 §6-6, §8), 이 화면은 그 판정을
  **표시**할 뿐이다.
- **X-4′ 전환 절차 UI의 설계가 아니다**(Q6).
- **V2-BAND 관련 어떤 화면 요구도 만들지 않았다**(§0 범위).
- **기존 `admin-staking-debt-visibility-frd.md`의 폐기 선언이 아니다.** 그 문서의 원리(§3.1의
  "승계" 열)는 이 문서 안에서 계속 구속력을 갖는다. 폐기되는 것은 **데이터 계약과 화면 위치**뿐이며,
  컷오버 전까지 기존 구현은 그대로 유효하다.
