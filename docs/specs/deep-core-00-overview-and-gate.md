## 1. 컴플라이언스 게이트 — 먼저 읽을 것

### 1.1 게이트 상태: **미해제**

> **[2026-08-10 갱신]** 이 절은 `pm` 사인오프 이전의 상태 기술이다. 현재 상태는 **§6**이 정한다:
> Phase 0 **승인**, Phase 1 설계 **원칙 승인**, Phase 1 구현 **게이트 유지**(해제 조건 §6.2).

본 기획의 핵심 요청인 **"게임 스탯(채굴 속도)이 실제 스테이킹 보상에 반영된다"** 는,
`game-planner`의 운영 규칙상 **"게임 결과가 BANA 토큰/포인트/랭크/발행량을 크레딧하는 메커닉"**
에 정확히 해당한다. 이 범주는 UI 기능이 아니라 **서버 권위 원장(server-authoritative ledger)
과 남용 방지 설계를 전제로 한 금전 산출물 기능**이며, `pm`의 명시적 사인오프 없이는 상세 스펙을
확정할 수 없다.

따라서 본 패밀리는 다음과 같이 처리했다.

- **04번 문서는 "결정용 제안서(decision-ready proposal)"로 작성했다.** 수식, 상한, 원장 스키마,
  남용 방지 항목을 전부 갖췄으나 문서 상태는 `pm 사인오프 대기`이며, 사인오프 전에는
  `game-developer`·`prisma-db-expert`가 착수하면 안 된다.
- 03번 문서 중 **CC(코어 크레딧) → 장비 → 수익 보너스로 이어지는 경로**는 04번과 동일 게이트에
  묶인다. SV(샐비지) → 코스메틱 경로는 게이트 밖이다.
- 이 게이트 문항이 본 기획의 **1번 오픈 퀘스천**이다(§4).

사용자가 "게임 스탯이 실제 보상에 영향을 준다"는 정책 방향을 이미 밝혔다는 점은 전달받았고 설계에
반영했다. 다만 그 전달 자체가 게이트 해제는 아니다 — 해제는 `pm`이 이 문서 §4의 Q1에 명시적으로
답하는 시점에 이루어진다.

### 1.2 게이트를 통과시키기 위해 본 기획이 미리 채운 조건

리서치 §5(FCA·SEC/FTC·확률형 규제)와 `docs/patterns/game-planner.md`의 컴플라이언스 패턴을
근거로, 04번 제안서는 아래 안전장치를 **설계 자체에 내장**했다. 사후에 덧붙이는 고지가 아니다.

| # | 안전장치 | 근거 |
|---|----------|------|
| A1 | **계약 이율 불변.** 게임은 `StakePosition.dailyRatePct` / `paidInterest`를 절대 수정하지 않는다. 보너스는 완전히 분리된 원장 행(`GameBonusPayout`)으로만 존재한다 | 포지션의 rate/term은 체결 시점 스냅샷 = 사용자와의 계약. 게임이 이를 사후 변경하면 계약 변경이 된다 |
| A2 | **하드 상한 +10.00%p(비율 상한) + 코인별 1일 절대 상한 + 사용자별 1일 절대 상한 + 프로그램 전체 일 예산** — 4중 상한 | 리서치 §3 "곱연산 스택의 후반 인플레이션" 경고 |
| A3 | **확률형 요소 전면 배제.** 랜덤박스·가챠·확률 드롭·미공개 확률 일절 없음. 상점은 100% 확정형(가격↔효과 고정 공시) | 리서치 §5 루트박스 규제(벨기에/네덜란드 금지, 폴란드 2025 개정, 한국 확률 공시 의무) |
| A4 | **수익에 영향을 주는 레이어는 영구·확정·무기한.** 타이머·소모품·한정 판매 등 긴급성(FOMO) 장치는 **코스메틱에만** 허용하고 수익 경로에는 일절 두지 않는다 | FCA "리스크 감수 유도" 프레임 회피 |
| A5 | **리더보드·랭킹·타 사용자 비교 없음.** 경쟁 서열 UI 자체를 만들지 않는다 | FCA가 명시한 우려 대상(포인트 집계·리더보드·배지·축하 메시지) |
| A6 | **끊기는 연속 출석(streak) 없음.** 누적만 증가하는 "총 가동일" 오도미터로 대체 | `docs/patterns/game-planner.md` — 실화폐로 유지되는 스트릭은 다크패턴 |
| A7 | **원금(principal) 비례 성장 금지.** XP·CC는 전부 정수형·코인 무관 수량(정산된 일수, 포지션 수, 약정일수)에서만 파생 | 동 패턴 라이브러리 + 리포지토리에 가격 피드가 없어 코인 간 원금 비교가 애초에 불가능 |
| A8 | **최대치가 시간만으로 도달 가능.** 보너스 상한(10%)은 예치 규모가 아니라 경과 일수로 도달한다 | 상한이 자금력으로만 도달 가능하면 그 순간 업셀 사다리가 된다 |
| A9 | **소급 적용 절대 금지.** 장비 구매·레벨업은 **다음 정산일부터** 반영. 정산 시점 MP를 행에 스냅샷 | 이미 발생한 이자에 소급 보너스를 붙이는 순간 회계·감사 문제 |
| A10 | **관리자 지급 포지션(`grantedByAdminId != null`) 보너스 제외** | 기존 auto-renew 자격 규칙과 동일한 배제 기준 승계 |
| A11 | **게임 보너스는 MLM 레퍼럴 보너스 산정 기준액에서 제외** | `payReferralBonuses`는 이자의 %를 지급 — 제외하지 않으면 게임이 발행량 배수기가 된다 |
| A12 | **관할별 킬 스위치.** `PlatformSetting`에 전역/지역 단위 on-off. 중단은 항상 **장래효**이며 소급 회수(clawback)는 없다 | 리서치 §5 — 한국/벨기에/네덜란드/폴란드 등 관할별 편차. BANA는 6개 로케일 서비스 |
| A13 | **모든 게임 텍스트는 DOM 오버레이.** 캔버스 텍스처에 문자열을 굽지 않는다 | 텍스처에 구운 고지 문자열은 테스트로 린트할 수 없음(`docs/patterns/game-planner.md`) |
| A14 | **법적 고지는 절대 NPC 대사로 전달하지 않는다.** 세계관 캐릭터가 규정을 말하는 연출은 금지 | 고지의 진지성 희석 방지 |

### 1.3 이 기획이 **하지 않는** 것 (명시적 제외)

- 실화폐 결제(IAP) 없음. 두 재화 모두 현금 구매 불가.
- 재화의 사용자 간 이전·거래·2차 시장 없음. NFT 없음. 토큰화 없음.
- 재화의 현금·코인 환전 없음. 재화 자체에 금전적 가치 없음(고지 문구로 명시).
- 조기 해지·가속 인출·포지션 매도 등 **기존 스테이킹 상품 사양을 바꾸는 메커닉 없음**
  (현 코드에 조기 언스테이크 엔드포인트 자체가 없음).
- 확률형 요소·경매·경쟁 랭킹 없음.

## 2. 페이즈 분리 — 게이트가 안 열려도 절반은 나간다

게이트 결과와 무관하게 진행 가능한 범위를 분리했다. `pm`이 Q1에 "아니오"라고 답해도 Phase 0은
그대로 살아남으며, 그 경우 게임은 **순수 코스메틱 진행형 시각화**로 출시된다.

| Phase | 범위 | 게이트 | 새 DB |
|-------|------|--------|-------|
| **P0 — 채굴 현장** | 세계관, Phaser 캔버스, 60레벨/XP(정산 일수 파생), 챕터 6단계 배경·장비·크루 외형 변화, 총 가동일 오도미터, SV(샐비지) → 코스메틱 상점 | 불필요 | 필요(게임 상태 영속화). 금전 산출물 아님 → 일반 제품 작업 |
| **P1 — 채굴력 연동** | CC(코어 크레딧), 5×10 장비 트랙, MP 산출, **MP → 실제 보너스 지급** | **필수** | `GameBonusPayout` 등 금전 원장 |
| **P2 — 심층 확장** | 챕터 7+ , 시즌 이벤트, 크루 서사 확장 | P1 결과에 따름 | — |

P0가 새 테이블을 요구한다는 점은 정직하게 적어 둔다. `docs/patterns/game-planner.md`의
"새 테이블/컬럼/쓰기가 없다 = 코스메틱" 트립와이어 기준으로는 P0도 코스메틱 순수형은 아니다.
다만 **금전 산출물이 없으므로** 컴플라이언스 게이트가 아니라 일반 제품·DB 리뷰(`prisma-db-expert`)
대상이다. 이 구분을 흐리지 말 것.

## 4. `pm`에게 올리는 오픈 퀘스천 (우선순위 순)

> **[2026-08-10]** 전 문항 답변 완료 — **§6.5** 참조.

**Q1 (게이트, 최우선).** 게임 스탯(MP)이 실제 스테이킹 지급액을 증가시키는 것을 승인하는가?
04번 문서 §2의 수식과 §5의 4중 상한을 전제로 한다. 승인 시 함께 확정 필요:
(a) `GAME_BONUS_MAX_PCT` 최종값(제안 10.00%), (b) 보너스 재원(플랫폼 예산 항목),
(c) 관할별 적용 범위(6개 로케일 중 어디까지), (d) 법무 검토 착수 여부.

**Q2.** 사용자가 언급한 "입금액 기반 포인트 적립"을 **채택하지 않을 것을 권고**한다(A7).
근거: (i) 가격 피드가 없어 코인 간 비교 불가, (ii) 보너스가 이미 이자에 비례 = 원금에 비례하므로
포인트까지 원금 비례로 두면 원금이 이중으로 곱해진다, (iii) 결과적으로 예치 증액을 유도하는
업셀 구조가 되어 FCA 프레임에 정면으로 걸린다. 대체안(활성 포지션 수 3개 상한 + 약정일수)은
03 문서 §2에 설계되어 있다. **이 권고를 수용하는가?**

**Q3.** 6개 관할(en/ko/ja/zh/vi/th) 각각에서 "인게임 재화로 구매한 확정형 아이템이 실제 수익률을
높이는 구조"의 규제 취급에 대한 1차 법령 조사가 필요하다. 리서치 문서 §Open Questions도 동일
지점에서 `/deep-research`를 권고했다. **법무·리서치 착수를 지시하는가?**

**Q4.** Phase 0 단독 출시(게임 스탯 = 순수 시각화)를 P1 승인과 무관하게 진행하는가?
P0만으로도 완결된 제품이며, P1 미승인 시의 폴백이자 P1 승인 시의 1단계다.

**Q5.** 최대 레벨 도달 시간 목표를 **단일 포지션 사용자 기준 약 647일(약 21개월)** 로 잡았다

### 6.0 판정 요약

### 6.1 게이트를 지금 열지 않는 결정적 이유 — EQ-1은 엔지니어링 질문이 아니라 선결 조건이다

`docs/patterns/pm.md`("승인의 근거가 되는 주장은 코드로 검증한다")에 따라 직접 확인한 결과,
04 문서 §10 EQ-1은 `game-planner`가 분류한 "미해결 엔지니어링 질문"보다 **한 단계 위의 문제**다.

**확인된 사실: 현재 스테이킹 이자에는 사용자에게 지급되는 경로가 존재하지 않는다.**

| # | 사실 | 출처 |
|---|------|------|
| C1 | `runStakingSettlement`은 `StakingPayout` 행 생성 + `paidInterest`/`daysPaid` 갱신만 한다. 어떤 잔고도 크레딧하지 않는다 | `web/src/lib/stakingSettle.ts:67-91` |
| C2 | 출금 가능액 = **Nia 잔고 − 잠긴 원금**. `paidInterest`는 이 식에 들어가지 않는다 | `web/src/app/api/nia/withdrawals/route.ts:231` |
| C3 | 원금도 실제로 이동하지 않는다. 스테이킹은 Nia 잔고를 **소프트 락** 하는 장부 조작이며, 코인은 사용자 Nia 지갑에 그대로 있다 | `web/src/app/api/staking/stake/route.ts:116-133`, `schema.prisma:251-253` |
| C4 | `ReferralBonusPayout`도 동일하게 행만 만들고 잔고를 건드리지 않으며, env로 OFF 상태다 | `web/src/lib/referralBonus.ts:48` |
| C5 | 그럼에도 `/staking`은 `paidInterest` 합계를 **"Rewards Earned"로 사용자에게 이미 표시**하고 있다 | `web/src/components/Staking.tsx:375-383` |

즉 BANA의 스테이킹 이자는 현재 **BANA 자체 Postgres에만 기록된 미결제 채무**다. 04 문서는
`GameBonusPayout`을 "`StakingPayout`과 동일 레일"에 올린다고 설계했는데, **그 레일은 지급으로
끝나지 않는다.** 따라서 지금 게이트를 열면 다음이 발생한다.

1. **지급 방법이 정의되지 않은 채무를 게임이 키운다.** 게임 보너스는 "실제 지급액 증가"라는
   약속으로 판매되지만, 실제로는 C5의 표시 숫자를 키울 뿐이다. 이미 표시 중인 미지급 금액에
   게임 서사와 진행 보상이라는 정당성까지 붙는 순간, 이는 단순한 미구현이 아니라 **표시상의
   오인 유발** 영역으로 넘어간다.
2. **나중에 지급 레일이 생길 때 규모가 통제 밖에서 결정된다.** 훗날 Nia-Hub 크레딧이든 재무
   수동 이체든 지급 경로가 만들어지는 시점에, 누군가는 "`GameBonusPayout`도 포함하는가"를
   결정해야 한다. 그때는 이미 원장에 수개월치 행이 쌓여 있고, 그 결정은 설계 판단이 아니라
   **기정사실 추인**이 된다. 04 §5.4의 월 예산 상한은 그 시점에 소급 적용할 수 없다.
3. **04 §5.4의 "장래효 정지, 소급 회수 없음" 원칙이 리스크를 확대한다.** 이 원칙 자체는
   옳다(그대로 유지한다). 다만 회수가 없다는 것은 **잘못 발행된 행이 영구히 채무로 남는다**는
   뜻이므로, 발행을 시작하기 전에 지급 방법이 확정되어 있어야 한다는 요구가 더 강해진다.

`game-planner`가 EQ-1을 정직하게 적어 올린 것은 이 기획의 가장 큰 미덕이다. 다만 그것을
"스키마만으로는 완결되지 않는다"는 단서로 처리한 것은 **과소평가**였다. EQ-1은 04 문서의
나머지 전부에 선행한다.

### 6.3 `pm` 수정 요구 — 승인된 설계에 대한 구속적 변경

04 문서의 안전장치 A1~A14, 규칙 Y-1~Y-5, 4중 상한, AC-Y1~Y14는 **전부 그대로 승인한다.**
아래는 그 위에 추가되는 항목이며, **M-1은 Phase 0에도 즉시 적용된다.**

#### M-1 (Phase 0 즉시 적용) — `charter_open` 적립 상한 신설

**결함:** 02 §2의 `xp.charter_open`(40)과 03 §2.1의 `cc.charter_open`(40)에는 **어떤 상한도
없다.** AB-4가 막는 3포지션 상한은 `lift` 계열에만 걸려 있다. 그리고
`StakingProduct.minAmount`는 `String?` — **nullable**이다(`schema.prisma:240`). 최소 예치금이
설정되지 않은 상품이 하나라도 열려 있으면, 사용자는 먼지 금액의 포지션을 무제한 개설해
포지션당 40 XP + 40 CC를 farming할 수 있다.

**더 심각한 2차 결함 — 설계가 의도와 반대 방향의 인센티브를 만든다.** `charter_open`(개설 시
40)과 `charter_complete`(완주 시 `min(300, 10 × termDays/3)`)를 합산하면:

```
30일 약정:  (40 + 100) / 30일 = 4.67 /일
90일 약정:  (40 + 300) / 90일 = 3.78 /일
```

`charter_complete` 단독으로는 일당 3.33으로 약정 길이에 **중립**이도록 잘 설계되어 있다.
그러나 정액 개설 보상 40이 짧은 약정에 유리하게 작용해, **최적 전략이 "짧은 약정을 잘게 쪼개
반복 개설"** 이 된다. 이는 03 §2.3이 배제하려 한 "예치 증액 유도"를 축만 바꿔(금액 → 개설 횟수)
되살린 것이며, 동시에 해지·재예치 회전을 부추긴다.

**요구:**
1. `charter_open` 적립을 **정산일당 1건**으로 제한한다(멱등 키에 `dayKey` 포함).
2. `charter_open`은 `lift`의 **활성 포지션 3개 상한을 공유**한다 — 4번째 이상 활성 포지션의
   개설은 0 적립.
3. **게임이 활성화된 동안 `minAmount`가 null인 스테이킹 상품을 열 수 없다.** 관리자 상품
   생성·수정 경로에서 검증하거나, 최소한 `charter_open` 적립 조건에 `product.minAmount != null`
   을 넣는다.
4. AC 추가 — **AC-P11**: 동일 정산일에 포지션을 N개 개설해도 `xp.charter_open` 총합이 40을
   넘지 않는다. **AC-D11**: `minAmount`가 null인 상품의 포지션에는 `cc.charter_open`이
   적립되지 않는다.

M-1은 XP/CC 적립 규칙이므로 Phase 0 범위다. **P1 승인 여부와 무관하게 지금 반영한다.**

#### M-2 — `GAME_BONUS_MAX_PCT`는 10.00% 확정, 단 초기 운영값은 별건

코드 상수 `GAME_BONUS_MAX_PCT = 10.00`과 04 §5.1의 하드 어서션을 제안값 그대로 승인한다.
`PlatformSetting`으로는 **낮출 수만 있고 올릴 수 없다**는 AB-9의 구현을 **필수**로 못 박는다.
P1 최초 출시 시 운영 설정값은 10.00%가 아니라 **더 낮은 값에서 시작**하며, 실제 값은 G-3
확정 시점에 정한다. 상한과 초기값을 같은 숫자로 두면 램프업 여지가 없다.

#### M-3 — "Rewards Earned" 표시와 게임 보너스 표시의 분리

C5의 기존 표시(`paidInterest` 합계)와 게임 보너스 누계를 **절대 합산해 하나의 숫자로 보여주지
않는다.** 항상 별개 행·별개 라벨로 표시한다. 이는 Y-1(원장 분리)의 UI 대응물이며,
`game.bonus.disclosureSeparate`가 문구로만 남고 화면에서는 합산되는 사태를 막는다.
**AC-Y15** 추가: 게임 보너스 금액이 `totalByCoin` 어느 값에도 합산되지 않는다.

#### M-4 — 킬 스위치의 되돌림 가능성을 제품 요구사항으로 고정

`docs/patterns/pm.md`("Reversibility is a product requirement")에 따라, `gameBonusEnabled = false`
전환 시 **게임 표면 전체가 아니라 보너스 지급만** 멈추고, 스테이킹 화면의 모든 기존 숫자가
게임 도입 이전과 **동일**해야 한다. 이것은 번들 위생이 아니라 **철수 가능성** 요구사항이며
구현 중 트레이드 대상이 아니다. AC-Y8이 절반을 담당하므로 나머지 절반(UI 동일성)을
**AC-Y16**으로 추가한다.

### 6.4 EQ-3 판정 — `User.locale`은 관할 통제 수단이 될 수 없다 (오픈 퀘스천 → 확정 사항)

04 §10은 EQ-3을 "locale 판별은 근사치일 뿐"이라고 적었다. 이는 **과소 서술**이다.
`locale`은 사용자가 설정 화면에서 **언제든 스스로 바꿀 수 있는 UI 언어 선호값**이다. 따라서
`gameBonusLocales`는 근사치가 아니라 **사용자가 직접 해제할 수 있는 잠금장치**이며, 통제
수단으로 성립하지 않는다. 특정 관할을 제외하라는 법률 판단이 나오는 순간 그것으로는 집행할 수 없다.

**결정:**
- `gameBonusLocales`를 **관할 통제 목적으로 사용하는 것을 금지한다.** 필드를 남기더라도 용도는
  "해당 언어권 UI 노출 제어"까지이며, 04 §6.1 표의 설명을 그렇게 고쳐 적는다.
- 현시점에 집행 가능한 관할 통제는 **전역 킬 스위치(`gameBonusEnabled`) 하나뿐**이다.
  6개 관할 중 한 곳이라도 불가 판정이 나오면, 별도 판정 필드가 생기기 전까지는
  **전 관할 미출시**가 유일한 선택지다. 이 사실이 G-2에 포함된다.
- 거주국·KYC 기반 판정 필드의 도입은 KYC 레벨 설계와 함께 다뤄야 할 **별도 제품 과제**다.
  본 기획이 그 과제를 촉발시켜서는 안 된다 — 게임 때문에 KYC 스키마를 바꾸는 것은 꼬리가
  몸통을 흔드는 순서다.

### 6.5 Q1~Q5 개별 답변

**Q1 — 설계 승인, 구현 착수 보류.** §6.0~§6.3이 답이다. 세부 항목:
- **(a) `GAME_BONUS_MAX_PCT`:** 10.00%로 확정. 단 M-2(초기 운영값은 더 낮게, 하향만 가능).
- **(b) 재원:** 미정 → G-3으로 이관. 이것이 해제 조건이다.
- **(c) 관할 범위:** 미정. §6.4에 의해 현재는 **전부 아니면 전무**. G-2로 이관.
- **(d) 법무 검토:** 착수 지시(Q3).

**Q2 — 권고 수용. 원금 비례 적립은 채택하지 않는다.** 대체안(활성 포지션 3개 상한 +
약정일수 기반)을 채택하되 **M-1을 반드시 함께 적용**한다 — 대체안이 그대로는 개설 횟수 축으로
같은 문제를 남기기 때문이다.

사용자(마스터)의 원래 요청을 뒤집는 결정이므로 근거를 명시한다. **핵심은 "원금 비례가 이미
구조적으로 달성되어 있다"는 점이다.** 보너스는 `base(p) × bonusPct`이고 `base(p)`는 원금에
비례한다 — 원금이 10배인 사용자는 **이미 10배의 보너스 금액**을 받는다. 여기에 포인트 적립까지
원금 비례로 두면 원금이 두 번 곱해져, 대형 예치자와 소액 예치자의 격차가 제곱으로 벌어진다.
즉 이 권고는 사용자 요청의 **거부가 아니라, 요청이 이미 충족되어 있으니 중복 적용을 막는 것**
이다. `game-planner`가 든 두 근거(가격 피드 부재, FCA 업셀 프레임)도 독립적으로 타당하다.

**Q3 — 착수 지시. 단 범위를 좁혀서 지시한다.**
- 1차: `researcher`가 6개 관할(en/ko/ja/zh/vi/th) **비구속 예비 조사**를 수행한다.
  **이 조사는 법률 자문이 아니며, 본 하네스의 어떤 에이전트도 법률 자문을 제공하지 않는다.**
  산출물은 인간 법률 자문에게 넘길 쟁점 정리까지다.
- **조사 초점을 재지정한다.** 04 문서는 확률형 규제(루트박스)를 주요 축으로 잡았으나 A3에 의해
  확률형 요소가 전면 배제되었으므로 그 축의 노출은 이미 대부분 닫혀 있다. **실제 쟁점은
  (i) 참여도에 따라 변동하는 수익 증분이 스테이킹 상품의 규제상 성격을 바꾸는가, (ii) 그 증분을
  판촉에 사용할 때의 광고·유인 규제** 두 가지다. 이쪽에 조사 자원을 배분한다.
- 2차: 인간 법률 자문 회신 = G-2의 구성 요소.

**Q4 — 예. Phase 0을 P1과 무관하게 단독 진행한다.** 이 사인오프에서 가장 확실한 부분이다.
P0는 금전 산출물이 없고, 그 자체로 완결된 제품이며, P1 승인 시 1단계가 된다.
`game-designer`(비주얼·자산)와 `game-developer`(Phaser 구현)는 **지금 착수한다.** 단:
- P0 범위에서 **CC(코어 크레딧)·장비 트랙·MP·보너스 관련 UI를 만들지 않는다.** 자리만
  비워두는 것도 금지 — "곧 출시" 류의 예고 표시가 있으면 그 자체가 A4(수익 경로 FOMO 금지)에
  걸린다. SV·코스메틱 경로만 구현한다.
- M-1을 P0 구현에 포함한다.
- `prisma-db-expert`는 P0 스키마(`GameProfile`, `GameXpEntry`, `GameLedgerEntry`의 SV 부분)만
  마이그레이션한다. `GameBonusPayout`과 `PlatformSetting`의 `gameBonus*` 필드는 **P1 게이트
  해제 전까지 마이그레이션하지 않는다.**

**Q5 — 647일 유지. 지금 단축하지 않는다.**
`game-planner`는 이를 리텐션 목표 대비 판단으로 올렸으나, **이것은 리텐션 곡선이 아니라 채무
증가 일정이다.** 최대 레벨 도달 시간을 줄이면 사용자당 최대 노출(+10%)에 도달하는 속도가 그만큼
빨라진다. 재원(G-3)이 확정되지 않은 상태에서 이 숫자를 줄이는 것은 예산을 정하기 전에 지출
속도를 올리는 것과 같다. **G-3 확정 이후 재검토 대상**으로 남기며, 그때는 리텐션이 아니라
예산 소진 곡선을 기준으로 판단한다. 이 항목을 `pm`에게 올린 판단은 옳았다 — 다만 그 이유는
문서에 적힌 것과 다르다.

### 6.6 문서 사실 정정 — §3의 "빌드 파손" 주장은 현재 사실이 아니다

§3은 `web/src/components/Staking.tsx:9`가 삭제된 `OilFieldEmbed`를 import 하고 `:389`에서
렌더하며 "현 작업 트리는 빌드가 깨진 상태로 보인다"고 적었다. **직접 확인한 결과 이 주장은
현재 사실이 아니다.** 해당 import는 이미 제거되었고, `:365-372`에 제거 사유를 적은 주석이
남아 있을 뿐이다(`field-live` 문자열의 전체 검색 결과가 그 주석 1건). 잔여물 정리 작업을
`web-wallet-expert`/`qa-lead`에 배정할 필요가 **없다.**

방향(코드를 읽고 근거를 제시)은 옳았고, 이는 검사 시점과 작업 트리 상태의 차이로 보인다.
다만 사인오프 문서에 남은 거짓 사실은 다음 담당자의 작업을 낭비시키므로 여기서 정정한다.
**§3의 나머지 항목(phaser 3.90.0 잔존, 960×540 엔진 설정 승계, 매일 정산, `stakingDayMs()`
하드코딩 금지, 가격 피드 부재)은 재확인 결과 전부 정확하다.**
