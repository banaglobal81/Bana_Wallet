## 2. XP 소스

| 소스 ID | 조건 | XP | 상한 |
|---------|------|-----|------|
| `xp.lift` | `StakingPayout` 행이 새로 기록될 때, 행 1개당 | **10** | 1 정산일당 **최대 3개 포지션**까지만 집계 → 일 최대 30 |
| `xp.presence` | 해당 정산일 키에 사용자가 앱을 1회 이상 열었고, 활성 포지션이 ≥1일 때 | **5** | 1일 1회. **연속 보너스 없음, 배수 없음, 놓쳐도 잃는 것 없음** |
| `xp.charter_open` | 새 포지션 개설 1건당(1회성) | **40** | 갱신(autoRenew)으로 생성된 승계 포지션은 **제외** |
| `xp.charter_complete` | 포지션이 `MATURED`로 전이하고 `daysPaid >= termDays`일 때 | **`min(300, 10 × termDays / 3)`** | 약정일수 비례(정수·코인 무관). 90일 약정 = 300 |

**표준 사용자 모델 (밸런싱 기준선)**
- *단일 포지션 사용자*: 15 XP/일 (`lift` 10 + `presence` 5)
- *3포지션 사용자*: 35 XP/일 (`lift` 30 + `presence` 5) — 상한에 걸려 **최대 2.33배**
- 4번째 이상 포지션은 XP를 늘리지 않는다. 이것이 P-2를 지키는 장치다.

**`xp.presence`에 대한 주석 (필수 유지)**
사용자 요청의 "로그인/활동" 항목을 반영하되, 리서치 §5가 지목한 FCA 우려(잦은 푸시·포인트 집계로
거래 12% 증가)와 `docs/patterns/game-planner.md`의 "실화폐로 유지되는 스트릭 = 다크패턴" 규칙을
동시에 만족시키기 위해 다음을 강제한다:
1. 연속일 카운터를 **저장하지도 표시하지도 않는다**.
2. `xp.presence` 미획득에 대한 알림·푸시·배지·"놓쳤습니다" 문구를 **일절 만들지 않는다**.
3. 전체 XP에서 차지하는 비중을 33%(단일 포지션) 이하로 유지 — 방문 자체가 주된 성장 수단이
   되면 그 순간 앱은 방문을 유도하는 구조가 된다.

## 3. XP 곡선 — 선택과 근거

### 3.1 결론

**최대 레벨 60. 다항(멱함수) 곡선을 채택한다.**

```
XPToNext(L) = 5 × ceil( (10 + 3 × L^1.15) / 5 )      (L = 1 … 59)
```

- L1→2 = **15 XP** (단일 포지션 사용자 기준 하루)
- L59→60 = **340 XP**
- 누적(L1→L60) ≈ **9,700 XP**
- 마지막 레벨 비용 / 첫 레벨 비용 ≈ **23배** (지수형이면 수만 배가 된다)

### 3.2 리서치가 제시한 3종을 각각 기각한 이유

리서치 §3은 (1) 선형, (2) 지수형(계수 Y≈1.4), (3) 피보나치형을 제시했다. 셋 다 채택하지 않았다.

| 후보 | 기각 사유 |
|------|-----------|
| **선형** | 초반 성취감이 없다. 방치형 장르의 핵심인 "첫 30분 안에 여러 번 오르는" 감각을 만들지 못한다 |
| **지수형 (×1.4)** | L60 도달 XP가 `1.4^59 ≈ 3.4×10^8` 스케일 — 사실상 도달 불가. **도달 불가능한 최대 레벨은 여기서 단순한 밸런싱 실패가 아니라 컴플라이언스 실패다**: 04 문서의 보너스 상한이 레벨에 묶여 있으므로, 레벨 상한이 시간으로 도달 불가하면 남는 도달 경로는 자금력뿐이고 그 순간 P-4/A8이 깨진다 |
| **피보나치형** | 리서치는 "초반 쉬움→중반 안정→후반 도전"으로 서술했으나, 피보나치 수열의 점근 성장비는 **φ ≈ 1.618** 로 지수형(1.4)보다 **오히려 가파르다**. 리서치의 이 서술은 초반 20~30항의 체감을 일반화한 것으로 보이며, 60레벨 구간에 적용하면 지수형과 같은 이유로 기각된다 |

### 3.3 다항 곡선을 고른 실제 이유

1. **초반은 지수형만큼 빠르다.** L1→L10에 267 XP ≈ 18일. 첫 세션에 1~2레벨이 오른다.
2. **후반이 도달 가능하다.** 지수형의 "후반 급경사"를 유지하되 발산하지 않는다 —
   성장률이 `L^0.15`로만 커지므로 마지막 구간에서도 하루 단위 진전이 체감된다.
3. **상한이 시간의 함수가 된다.** 최대 레벨까지 필요한 것은 자금이 아니라 **약 647일**이다.
   "이 게임의 최대치는 누구나 도달할 수 있고, 다만 오래 걸린다"는 문장을 그대로 쓸 수 있다.
4. **런타임 권위는 수식이 아니라 표.** 위 수식은 *출처 문서*이고, 구현체는 이 수식으로 생성한
   **동결된 60행 상수 테이블(`XP_TABLE`)** 을 쓴다. 단위 테스트로 테이블 전체를 잠근다.
   부동소수 `Math.pow` 결과가 환경/버전에 따라 흔들리며 레벨이 달라지는 사고를 원천 차단한다.

### 3.4 마일스톤 테이블 (설계 목표치, ±2%)

누적 XP는 `XP_TABLE` 생성 후 확정한다. 아래는 밸런싱 검수용 기준선이다.

| 레벨 | 해당 레벨 요구 XP | 누적 XP(근사) | 단일 포지션(15/일) | 3포지션(35/일) |
|------|------------------|---------------|--------------------|----------------|
| 2 | 15 | 15 | 1일 | 1일 |
| 5 | 30 | 75 | 5일 | 2일 |
| 10 | 55 | 267 | 18일 | 8일 |
| 15 | 80 | 578 | 39일 | 17일 |
| 20 | 105 | 1,019 | 68일 | 29일 |
| 25 | 135 | 1,591 | 106일 | 45일 |
| 30 | 160 | 2,305 | 154일 | 66일 |
| 35 | 190 | 3,164 | 211일 | 90일 |
| 40 | 220 | 4,171 | 278일 | 119일 |

## 5. 프레스티지 — 채택하지 않는다

리서치 §3은 Clicker Heroes식 어센션(진행 초기화 ↔ 영구 배율)을 장기 리텐션의 대표 패턴으로
제시하면서, 동시에 "원금이 실재하는 도메인에는 그대로 적용하기 어렵다"고 관찰했다.

**결론: 초기화형 프레스티지를 도입하지 않는다.** 근거:

1. **초기화의 대상이 없다.** 게임 진행(레벨·장비)은 실제 자금 활동에서 파생된 기록이다.
   이를 리셋한다는 것은 "사용자가 실제로 예치했던 기간의 기록을 지운다"는 뜻이며,
   금융 화면에서 기록 삭제는 그 자체로 감사·신뢰 문제다.
2. **P-3(XP 비감소)과 정면 충돌한다.**
3. **"리셋하면 더 벌 수 있다"는 구조는 04 문서의 상한 설계를 무력화한다.** 배수를 얻기 위해
   초기화를 반복하게 만드는 순간, 상한은 "반복 횟수"로 우회되는 상한이 된다.

### 5.1 대체안 — 「심층 기록 / Core Log」 (레벨 60 이후 메타 트랙)

- 레벨 60 도달 후에도 XP는 계속 적립되며, **2,000 XP마다 「심층 기록」 1단**이 오른다(무한).
- 보상은 **100% 코스메틱**: 명판 각인, 리그 도장, 크루 복장 변형, 배경 이펙트, 지층 조명 프리셋.
- **채굴력(MP) 0. 수익 영향 0.** 이 문장을 UI에 상시 표기한다(05 문서 §6, `game.coreLog.noYield`).
- 아무것도 초기화하지 않는다. 이름도 "프레스티지"·"환생"·"승급"이 아니라 **"기록"** 이다 —
  경쟁·재시작 뉘앙스를 지운다.

### 5.2 총 가동일 오도미터

`docs/patterns/game-planner.md`의 지시대로, 스트릭 대신 **감소하지 않는 누적 카운터**를 둔다.

- 정의: 사용자에게 `StakingPayout` 행이 하나라도 기록된 **서로 다른 정산일 키의 개수**.
- 표시: 리그 상단 HUD에 상시. `총 가동일 1,204일`.
- 끊김 개념이 없다. 쉬었다 돌아와도 숫자는 그대로 이어진다.
- 이 수치는 어떤 보상에도 연결되지 않는다. 순수 기록.

## 6. 데이터 모델 요구 (Phase 0)

`prisma-db-expert` 소관. 게임 상태는 **파생 가능한 것은 파생하고, 파생 불가능한 것만 저장**한다.

```
GameProfile
  userId            String  @id        // BANA user id (세션 파생)
  xpTotal           Int     @default(0)
  level             Int     @default(1)   // xpTotal에서 파생되지만 조회 최적화 위해 비정규화
  chapter           Int     @default(1)   // level에서 파생. 동상
  svBalance         Int     @default(0)   // 샐비지(코스메틱 전용)
  ccBalance         Int     @default(0)   // 코어 크레딧 — P1에서만 사용
  operatingDays     Int     @default(0)   // 총 가동일 오도미터
  lastPresenceKey   String?               // xp.presence 1일 1회 멱등 키 (dayKey)
  cosmetics         Json    @default("{}")// 장착 코스메틱 슬롯
  createdAt / updatedAt
```

```
GameXpEntry                              // append-only 감사 로그
  id, userId, dayKey, source, amount, refId
  @@unique([userId, source, refId])       // 멱등성. refId = payoutId | positionId | dayKey
  @@index([userId, dayKey])
```

**쓰기 경로는 두 곳뿐이다.**
1. `runStakingSettlement` 내부 — `xp.lift` / `xp.charter_complete` (정산 트랜잭션과 동일 트랜잭션).
2. 인증된 서버 액션 — `xp.presence`(1일 1회, `lastPresenceKey`로 멱등), `xp.charter_open`(스테이크 체결 시).

클라이언트가 XP·레벨·재화를 POST 하는 엔드포인트는 **만들지 않는다**. 상점 구매도 금액을 클라이언트가
보내는 것이 아니라 아이템 ID만 보내고 서버가 가격표에서 조회한다(03 문서 §5).

## 7. 수용 기준 (AC)

| ID | 기준 |
|----|------|
| AC-P1 | `StakingPayout` 행이 없는 날에는 어떤 XP도 적립되지 않는다 |
| AC-P2 | 동일 정산일에 포지션 5개를 보유해도 `xp.lift`는 30을 넘지 않는다 |
| AC-P3 | 정산 워커를 껐다 켜도 XP 총합이 중복 적립되지 않는다(`@@unique` 검증) |
| AC-P4 | 어떤 경로로도 `xpTotal`이 감소하지 않는다 |
| AC-P5 | `XP_TABLE`은 60행 동결 상수이며, 테스트가 전 행의 값을 잠근다 |
| AC-P6 | 레벨 60 이후 XP가 계속 적립되고 「심층 기록」 단수가 오르되, MP는 변하지 않는다 |
| AC-P7 | 연속 방문일 수를 저장·표시·보상하는 코드가 존재하지 않는다(grep 가능한 금지어: `streak`) |
| AC-P8 | 원금(`principal`)을 읽어 XP를 산출하는 코드가 존재하지 않는다 |
| AC-P9 | 자동 갱신으로 생성된 승계 포지션에는 `xp.charter_open`이 적립되지 않는다 |
| AC-P10 | 클라이언트에서 XP/레벨/재화를 직접 증가시킬 수 있는 API 엔드포인트가 없다 |
