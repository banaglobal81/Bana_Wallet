## 0. 요약 — 이 문서의 여덟 가지 판정

| # | 판정 | 위치 |
|---|------|------|
| **S-1** | **S-STAKE의 빈 상태는 3개가 아니라 7개다.** §7.1이 준 ⓐ(상품 0건)/ⓑ(잔고 0)/ⓒ(T2 정지)에 더해, **컷오버 중(`MIGRATING`)·잔고 조회 실패·홀드로 잠긴 상태(`LOCKED_OUT`)·로딩**이 각각 다른 화면이다. 셋만 구현하면 나머지 넷은 **셋 중 하나로 잘못 렌더된다** — 특히 "조회 실패"가 "잔고 0"으로 렌더되는 것은 A-7 LB-7이 이미 금지한 실패 양식이다 | §3 |

## 1. Goal

**사용자가 ① 지금 체결할 수 있는지, ② 할 수 없다면 그 이유가 무엇이고 그것이 자기가 바꿀 수 있는 것인지,
③ 체결하면 정확히 무엇이 일어나고 무엇이 일어나지 않는지를 오해 없이 읽는다.**

| 답한다 | 답하지 않는다 |
|--------|---------------|
| S-STAKE 진입 상태 7종의 판별자·우선순위·렌더 | 픽셀·색·토큰 (→ `ui-ux-designer`, A-11/T-14) |

| 세 가지(+네 가지) 빈 상태의 카피와 금지 사항 | 상품을 언제 여는가 (CP-6 — 별도 관리자 액션, `pm`) |

## 3. 화면 상태 기계 — S-STAKE 진입 상태

### 3.1 일곱 상태와 판별자

**모든 판별자는 서버가 내려주는 명시 값이다**(LA-3). 클라이언트는 `alertStage`를 보고 "T2면 정지"
같은 규칙을 **재구현하지 않는다** — 그 규칙은 T1과 전환 중 상태를 놓친다(S-4/S-5).

| # | 상태 | 판별자 | 사용자에게 참인 문장 | LA-4 분류 |
|---|------|--------|---------------------|-----------|
| **E-0** | `LOADING` | 요청 진행 중 | — | 스켈레톤 |
| **E-1** | `MIGRATING` | `stakeRail !== 'LIVE'` (DC-1) | "제공되지만 지금 멈춰 있다" | **비버튼 상태칩** |
| **E-2** | `HALTED` | `newPositionState !== 'ALLOWED'` (DC-2) | "제공되지만 지금 멈춰 있다" | **비버튼 상태칩** |
| **E-3** | `NO_OFFERS` | `openProducts.length === 0` | "지금 개설된 오퍼가 없다" | **비버튼 상태칩** |
| **E-4** | `BALANCE_UNKNOWN` | 로컬 잔고 `state === 'error'` (DC-4) | "당신의 잔고를 확인하지 못했다" | **비버튼 상태칩** + 재시도 |
| **E-5** | `LOCKED_OUT` | `available < minRequired` **and** `holds.total > 0` | "당신 돈은 있으나 잠겨 있고, **시간이 지나면 풀린다**" | **비버튼 상태칩** + [내 포지션] |
| **E-6** | `NO_FUNDS` | `available < minRequired` **and** `holds.total === 0` | "채울 방법이 **없다**" | **비버튼 상태칩** |
| **E-7** | `READY` | 위 어느 것도 아님 | "지금 누를 수 있다" | 활성 버튼 |

`minRequired` = **OPEN 상품 중 `minAmount`의 최솟값**. CP-5′가 `minAmount` non-null을 강제하므로
이 값은 항상 존재한다. `null` 관측 시에는 **`E-4`로 떨어뜨린다**(모르는 값을 0으로 읽지 않는다).

### 3.2 우선순위 — 위에서부터, 첫 번째로 참인 것 하나만

```
E-0 LOADING  >  E-1 MIGRATING  >  E-2 HALTED  >  E-3 NO_OFFERS
             >  E-4 BALANCE_UNKNOWN  >  E-5 LOCKED_OUT  >  E-6 NO_FUNDS  >  E-7 READY
```

| 규칙 | 근거 |
|------|------|
| **`MIGRATING`이 최상위** | 경로 자체가 닫혀 있으면 나머지는 전부 무의미하다. 이 상태에서 "상품이 없습니다"라고 쓰면, 컷오버가 끝나고 상품이 열려도 사용자는 같은 화면을 다시 본다 |
| **`HALTED` > `NO_OFFERS`** | 정지는 **사건**이고 카탈로그 공백은 **상태**다. 정지를 카탈로그 공백 뒤에 숨기면, 상품이 열리는 순간 화면이 "없음"에서 "중지"로 **설명 없이 뒤집힌다.** 사건을 먼저 말한다 |
| **`NO_OFFERS` > `BALANCE_UNKNOWN`** | 오퍼가 0건이면 잔고 질문 자체가 발생하지 않는다. 여기서 "잔고를 불러오지 못했습니다"를 띄우는 것은 소음이며, 사용자가 자기 돈에 문제가 생겼다고 읽는다 |
| **`LOCKED_OUT` > `NO_FUNDS`** | **이 순서가 §5.2의 거짓말을 막는 유일한 장치다.** 홀드로 잠긴 사용자에게 *"BANA를 늘릴 방법이 없습니다"* 라고 쓰면 **거짓**이다 — 그의 돈은 만기에 돌아온다 |

> **`E-1`과 `E-2`의 문구를 같게 쓰지 않는다.** `MIGRATING`은 **우리가 계획해서 멈춘 것**이고
> (컷오버가 끝나면 풀린다는 사실을 우리는 안다), `HALTED`는 **사고 대응**이며 언제 풀릴지 모른다.
> 그래서 `MIGRATING`에만 "일시(temporarily)"를 쓰고, `HALTED`에는 쓰지 않는다(LA-5).
> **둘 다 원인은 설명하지 않는다.**

### 3.3 (S-4) `T1_WARNING` — A-7 AC-A7-08의 범위를 좁힌다

**실측:** `assertExecutionAllowed(symbol,'NEW_POSITION')`은 아래 네 경우에 예외를 던진다
(`web/src/lib/coinAuthority.ts:166-199`).

| 사유 코드 | 조건 | 사용자 체결 |
|---|---|---|
| `T2_HALTED` | `authorityAlertStage = T2_HALTED` | **거부** |
| `DIRECT_CHANGE_IN_PROGRESS` | 권위 직접 변경 진행 중 | **거부** |
| `TRANSITION_IN_PROGRESS` | 권위 전환 진행 중 | **거부** |
| `T1_WARNING_NO_OVERRIDE` | `T1_WARNING` **and** 관리자 오버라이드 없음 | **거부** (사용자 라우트에는 오버라이드가 없다) |

**충돌:** A-7 §3.4는 *"`T1_WARNING`에서 사용자 화면에 아무것도 표시하지 않는다"*, AC-A7-08은
*"T1의 렌더 결과가 CLEAR와 완전히 동일하다"*를 요구한다. 체결 표면에 그대로 적용하면
**활성 상태의 [예치] 버튼 → 403** 이 된다.

> **판정 T8-R1 (A-7 자체 개정 · `product-planner` 소관).** **AC-A7-08의 범위를
> "잔고 표시·출금·조회 표면"으로 좁힌다. 체결 표면(S-STAKE 및 그 진입점)에는 적용하지 않는다.**
> 근거 셋:
> ① A-7 §3.4의 원문 근거는 X-3′의 *"T1은 사용자 기능을 정지하지 않는다"* 인데, **코드는 T1에서
>    신규 체결을 정지한다**(신규 체결 = 신규 발행으로 취급 — `coinAuthority.ts:151-157` 주석).
>    즉 T1에서 "사용자 기능이 정지되지 않는다"는 전제가 체결에 대해서는 참이 아니다.
> ② A-7이 T1을 숨긴 이유는 *"아무 조치도 할 수 없는 사용자에게 불안만 준다"* 였다. 그 논리는
>    **체결 버튼을 누를 수 있다고 믿게 만든 뒤 실패시키는 것**을 정당화하지 않는다.
> ③ **T1과 T2의 사용자 문구를 구분하지 않으므로 정보 노출은 0이다**(S-5). 사용자가 보는 것은
>    "이 자산의 신규 체결이 중지됐다" 하나뿐이고, 그것은 **두 경우 모두 참**이다.
>
> **따라서 잔고 화면은 T1에서 여전히 CLEAR와 동일하게 렌더되고, S-STAKE만 `E-2 HALTED`가 된다.**
> 이 비대칭은 결함이 아니라 **X-3′의 2단계 설계가 체결에만 다르게 적용된다는 사실**의 정확한 반영이다.

### 5.2 ⓑ `E-6 NO_FUNDS` — 상품은 있으나 BANA 잔고가 0 · **가장 어려운 화면**

#### 5.2.1 이 화면이 어려운 이유를 정확히 적는다

세 가지가 동시에 참이다.

1. **사용자가 조건을 채울 수 없다.** 입금 레일 `UNSUPPORTED`, 클레임 OFF, 레퍼럴 OFF, 관리자
   크레딧은 **사용자가 쓸 수 있는 경로가 아니다**(rev05 §4A.1 AC-1).
2. **그런데 화면 모양은 "채우면 된다"고 말하기 쉽다.** 금액 입력 + 비활성 버튼은 이 프로젝트에서
   가장 만들기 쉬운 화면이고, **가장 정직하지 않은 화면**이다.
3. **"입금하세요"도 "문의하세요"도 쓸 수 없다.** 전자는 존재하지 않는 레일을 가리키고,
   후자는 **지원 채널을 입금 창구로 만든다**(§7.1 원문 금지).

#### 5.2.2 화면

```
┌─ 예치 ──────────────────────────────────────────────────┐
│  [ 체결할 수 없음 ]                  ← 비버튼 상태칩      │
│  스테이킹은 BANA 잔고에서 예치합니다                      │
│  사용 가능: 0 BANA                                        │
│  BANA는 입금할 수 없으며, 이 잔고를 늘릴 수 있는          │
│  다른 방법도 없습니다.                                    │
│  각 상품의 조건은 아래에서 확인할 수 있습니다.            │
│  ────────────────────────────────────────────────────    │
│  [상품 카드 · 읽기 전용]  일 0.2% · 10일 · 최소 100 …     │
│  [상품 카드 · 읽기 전용]  일 0.5% · 30일 · 최소 100 …     │
└─────────────────────────────────────────────────────────┘
```

| ID | 요구 |
|----|------|
| **EB-1** | 네 문장을 이 순서로 렌더한다: **① 무엇을 쓰는가 → ② 지금 얼마인가 → ③ 늘릴 방법이 없다 → ④ 조건은 볼 수 있다.** ②를 빼면 사용자는 자기 상태를 모르고, ④를 빼면 화면이 아무 쓸모 없어 보인다 |
| **EB-2** | **③은 조건부 렌더다.** `localDepositRail === 'UNSUPPORTED'` **and** `yieldRail !== 'CLAIM_LIVE'`일 때만 렌더한다. 어느 한쪽이라도 열리면 이 문장은 **거짓**이 되므로 **자동으로 사라져야 한다**(S-3). 조건이 깨졌는데 사라지지 않는 것을 AC로 잡는다(AC-T8-11) |
| **EB-3** | **③이 렌더되지 않는 경우(레일이 열린 뒤)** 대체 문구를 이 문서가 만들지 않는다. 그때의 화면은 **새 FRD의 대상**이며, 그 사이에는 ①②④만 렌더한다 — **모르는 것을 지금 지어내지 않는다**(A-7 §7.4 "빈 자리 예고 금지"와 같은 원칙) |
| **EB-4** | **금지 — 어떤 조건에서도:** 입금 주소·QR·네트워크 선택기 렌더, `/deposit`으로 가는 링크·CTA, 주소 생성 API 호출(rev04 N-6 / X-7). **네트워크 호출 0건**이 검증 형태다 |
| **EB-5** | **금지 — 문구:** "입금", "충전", "구매", "스왑", "고객지원에 문의", "관리자에게 문의", "곧", "준비 중", "아직", "잠시 후 다시 시도" |
| **EB-6** | **금지 — 구조:** 금액 입력 필드, 비활성 [확인] 버튼, 진행률·체크리스트("1단계 잔고 채우기 ✓/✗") |
| **EB-7** | 상품 카드는 **누를 수 없되 조건 전부(이율·기간·최소·최대·정원)를 표시**한다. 흐리게(opacity) 처리해 **읽기 어렵게 만들지 않는다** — 읽으라고 남긴 것이다 |
| **EB-8** | 이 블록은 **접기 안에 두지 않는다.** 사용자가 펼쳐야 보이는 설명은 없는 것과 같다 |

> **왜 "다른 방법도 없습니다"라고까지 쓰는가.** 여기서 멈추고 *"BANA 잔고가 0입니다"* 만 쓰면,
> 사용자는 **어딘가에 방법이 있는데 자기가 못 찾는 것**이라고 읽는다. 그 사용자가 다음에 하는 행동이
> **외부 주소로 BANA를 보내는 것**이며, 그것이 A-7 §7.2가 *"실제 자금 사고를 만든다"* 고 지목한 경로다.
> **모른다고 말하지 않는 것과, 없다고 말하는 것은 다르다. 우리는 없다는 것을 안다.**

> **관리자 크레딧(§4A)이 존재해도 이 문장은 그대로다.** 관리자 크레딧은 **내부 E2E 검증과 대사 정정**
> 전용이며(AC-1), 사용자가 요청해서 받을 수 있는 것이 아니다. 화면이 그 존재를 암시하는 순간
> **AC-1이 금지한 "일반 사용자 대상 지급"의 수요를 화면이 직접 만든다.**

### 6.3 왜 ⓐ(원금은 이동하지 않는다)를 맨 앞에 두는가

체결 화면에서 사용자가 가장 크게 오해하는 것은 **이자**가 아니라 **원금**이다. 소프트 락에서
사용자가 실제로 지는 위험은 손실이 아니라 **동결**이며(rev05 §3.2 ⓓ), 동결은 *"내 돈이 어디로
갔는가"* 라는 질문을 만든다. **ⓐ는 그 질문에 사전에 답한다** — 그리고 그것은 **참이다.**
이자에 대한 정정(ⓒⓓ)만 하고 원금을 설명하지 않으면, 가장 정확한 문장이 가장 불안한 화면이 된다.

| **AR-7** | **구버전 탭이 `autoRenew: true`를 담아 체결을 요청하는 경로**는 CP-5′(전 상품 `CLOSED`) 동안 **도달 불가능하다**(STEP 2에 갈 수 없다). 그럼에도 서버는 **조용히 무시하지 않는다** — 무시는 *"사용자가 본 약속을 우리가 안 지키는 상태"*(판정 V-4)를 재생산한다. **거부한다**(DC-11). 그 거부의 **전용 사용자 문구는 만들지 않고 `GENERIC` 폴백에 맡긴다**: 전용 문구를 만들면 갱신 어휘가 사용자 표면에 다시 등장하고(R-AR-4 부수 요구), 그 대가로 얻는 것은 **도달 불가능한 경로의 정확도**뿐이다 |

### 6.5 (개정 01) 설계 근거 — 세 가지 선택

**① 왜 비활성 토글이 아니라 미렌더인가.**
이 문서는 §5.2(S-2)에서 **비활성 버튼을 거부**했다. 근거는 *"비활성 컨트롤은 '기다리거나 채우면
눌린다'는 거짓 약속"* 이라는 것이었다. 자동갱신 토글에 그 논리를 적용하면 결론은 하나뿐이다 —
**비활성 토글은 "지금은 꺼져 있다"고 말하고, 사용자는 그것을 "나중에 켤 수 있다"로 읽는다.**
그리고 그것은 **T-20의 착수 시점이 정해지지 않은 지금 거짓이다.** 판정 V-5가 은닉을 허용한
근거(*"V2 포지션을 가져 본 사용자가 아직 0명"*)는 **A-7 §7.2의 은닉 경계에 대한 면제**이지
비활성 노출의 허가가 아니다. **없는 기능의 비활성 컨트롤을 보여 주는 것은 없는 기능을 광고하는 것이다.**

**② 왜 ⓔ에 합치지 않고 ⓕ로 분리하는가.**
ⓔ는 *"기록된 이자는 자동으로 옮겨지지 않는다"* 로 끝난다. 여기에 *"원금도 자동으로 다시 스테이킹되지
않는다"* 를 붙이면 **한 문장이 서로 다른 두 대상(이자·원금)에 대한 두 개의 부정을 지게 되고**,
사용자는 둘을 하나로 읽는다. 분리하는 실질적 이유는 하나 더 있다 — **T-20이 오면 ⓕ만 사라지고
ⓔ는 남는다.** 합쳐 두면 그날 **참인 절반까지 함께 지워지거나, 거짓인 절반이 함께 남는다.**
키를 분리해 두는 것이 **소멸의 단일 지점**을 만든다(CP1-10 · AC-T8-30).

**③ 왜 판정문의 어휘를 그대로 옮기지 않았는가 — 명시적 이탈 1건.**
R-AR-4는 *"만기에 원금이 **지갑으로 돌아오며** 자동으로 다시 스테이킹되지 않는다"* 로 적혀 있다.
그러나 **"지갑"은 A-7 T-8이 로컬 잔고에 대해 금지한 단어**이고, **"돌아온다/반환"은 N-20이 금지**했다
(원금은 나간 적이 없으므로 돌아오지 않는다 — §6.3). 판정문은 **정책 문서이지 카피 원본이 아니므로**,
요구의 **의미**를 이 문서의 확정 어휘로 옮긴다:

| R-AR-4의 절 | 이 문서의 담당 | 어휘 |
|---|---|---|
| *"만기에 원금이 지갑으로 돌아온다"* | **ⓔ `maturityNote`**(기존) | *"약정이 끝나면 원금의 잠금이 해제되어 {coin} 잔고에서 다시 사용할 수 있습니다"* |
| *"자동으로 다시 스테이킹되지 않는다"* | **ⓕ `noRestake`**(신규) | *"이 스테이킹은 약정이 끝나도 자동으로 다시 시작되지 않습니다"* |

**의미는 동일하고 어휘만 승계 규약(A-7 T-8 · N-20)을 따랐다.** `pm` 확인 대상으로 §13-7에 올린다.

### 7.2 에러 발생 후의 화면 전이 (중요)

**에러 문자열만 빨갛게 띄우고 끝내지 않는다.** 각 코드는 §3의 상태 중 하나가 참이 되었다는 뜻이므로,
화면은 **그 상태로 이동**해야 한다. 그러지 않으면 사용자는 실패한 STEP 3에 남아 같은 버튼을 다시 누른다.

| 코드 | 인라인 표시 | 전이 |
|---|---|---|
| `STAKE_PATH_MIGRATING` | STEP 3에 1줄 | **STEP 1 + `E-1` 블록**으로 되돌림. 목록 재조회 |
| `STAKE_COIN_HALTED` | STEP 3에 1줄 | **STEP 1 + `E-2` 블록**으로 되돌림 |
| `STAKE_INSUFFICIENT_LOCAL_BALANCE` | STEP 3에 1줄 | **잔고 재조회 후 상태 재평가.** `E-5`/`E-6`이면 그 블록으로, 아니면 STEP 2 유지(입력값 보존) |
| `STAKE_PRODUCT_CLOSED` / `FULL` | STEP 3에 1줄 | **STEP 1 재조회.** 해당 카드에 마감/정원 칩 |
| `UNAUTHENTICATED` | 기존 규약 | 시트 유지 + 로그인 유도, **입력값 보존**(PS-A EG-13) |
| 미매핑 / 네트워크 실패 | `GENERIC` | **시트·입력값 유지.** *"체결되지 않았습니다"* 라고 **단정하지 않는다** — 화면은 그것을 모른다. `[상태 새로고침]`으로 포지션 목록을 다시 읽게 한다(A-7 §4.4 규약 승계) |

> **마지막 행이 이 표에서 가장 중요하다.** 체결은 **홀드 생성 + 포지션 생성이 한 트랜잭션**이므로
> 부분 성공이 없지만, **응답을 못 받은 경우**는 여전히 존재한다. 그때 "실패했습니다"는 우리가
> 모르는 것을 아는 것처럼 쓰는 것이고, **재시도 버튼은 두 번째 포지션을 만든다.**
> 재조회만 제공한다.

### 9.4 번역 브리프 (PS-A §9.3 N-1~N-10, A-7 §8.6 N-11~N-15에 이어서)

| # | 지침 |
|---|------|
| **N-16** | **`noFundsNoPath`에 일시성 부사를 넣지 않는다**(아직 / yet / まだ / 暂时 / 目前 / tạm thời / ชั่วคราว). 이 문장은 **레일이 없다는 사실**이지 순서를 기다리는 상태가 아니다(A-7 N-13의 확장 적용) |
| **N-17** | **`migrating*`에는 "일시(temporarily)"를 허용하고, `halted*`에는 금지한다.** 전자는 우리가 계획한 창이고 후자는 사고 대응이다. 두 문구를 같은 표현으로 통일하지 않는다(§3.2) |
| **N-18** | **`recordedNotPaid` / `contractTerms`에 수령·지급 동사를 쓰지 않는다**(PS-A T-7 목록: paid / 지급 / 支払 / 发放 / trả / จ่าย). *"기록된다(recorded / 記録 / 记录 / được ghi nhận / บันทึก)"* 를 쓴다 |
| **N-19** | **`balanceSource`의 "입출금 계정"은 A-7 §8.1 `walletPage.groupCustody`와 동일 어휘를 쓴다.** 두 화면이 같은 것을 다른 이름으로 부르면 사용자는 세 번째 계정이 있다고 읽는다 |

## 12. 이 문서가 승인하지 않는 것 (명시)

- **상품 개설(CP-6)의 승인이 아니다.** 이 문서는 상품이 전부 `CLOSED`인 상태에서의 화면을 정한다.
  **R-AR-4는 CP-6의 선행 조건을 하나 늘린 것이며(판정 §9), 이 문서가 그 조건을 충족시킨 것이지
  CP-6을 연 것이 아니다.**
- **클레임 버튼·클레임 UI의 설계가 아니다.** `claimSeparate`는 클레임이 **없다는 사실**의 표기이며,
  클레임 화면은 A-7 §4가 이미 소유한다.
- **입금 레일의 설계가 아니다.** §5.2는 레일이 없는 동안의 표시만 정한다(Q-M5 미회신).
- **밴드 UI(밴드 미터·최대 가산율 표기)를 포함하지 않는다.** 전 상품 `maxBonusPctOfBase = "0"`(AC-C12).
- **CUT-4 배포 승인이 아니다.** 배포 순서와 게이트는 rev05 §5.1이 소유한다.
- **v1 라우트의 동작 변경을 지시하지 않는다.** CS-1′는 이미 확정된 요구이며 이 문서는 그 **표시**만 정한다.
- **(개정 01) 자동갱신 기능의 폐기 판정이 아니다.** ⓕ는 **오늘 참인 계약 조건**의 표기이며,
  T-20이 엔진을 켜면 `autoRenewRail`이 뒤집혀 **자동으로 사라진다**(CP1-10). 그때의 토글·확인
  다이얼로그 카피는 `staking-auto-renew-copy-spec.md`가 이미 소유하고 있으며 **이 문서가 다시 쓰지 않는다**
  (다만 그 카피가 홀드 모델 이전에 쓰였다는 점은 §13-6에 남겼다).
- **(개정 01) `AUTO_RENEW_V2_ENABLED`를 운영자 편집 대상으로 만드는 승인이 아니다.** DC-10은
  코드 상수의 값을 **읽기 전용으로 화면에 전달**할 뿐이며, 그 값을 바꾸는 유일한 방법은 배포다(판정 R-AR-1).
